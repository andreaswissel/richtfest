## Amp orb development

The repository includes executable `.agents/setup` and `.agents/resume` hooks and a supervised service manifest in `.amp/services.yaml`. These prepare isolated development machines, not Railway deployments.

Setup installs Bun at the version in the root `packageManager` field, runs `bun install --frozen-lockfile --linker=isolated`, and installs PostgreSQL 15, Poppler and Tesseract with German/English language data. The isolated linker preserves the workspace packages' different Zod versions. Bun and the system tools are available to fresh non-interactive login shells without activating a custom shell environment.

Setup creates `.env` only if absent, initializes `.data/postgres` on loopback port 5433, applies the existing migrations, and seeds the Alpha and Outsider test workspaces. It always migrates this local database, never a database named by inherited project secrets. Local PostgreSQL disables fsync and synchronous commits for speed; this database is disposable and must never hold customer originals. The setup-only PostgreSQL process stops before the snapshot is captured. Repeating setup preserves local configuration and records and does not duplicate seed identities.

Amp can reuse a matching project snapshot, skipping setup entirely. On a stale snapshot, setup rechecks installed packages and the Bun lockfile rather than downloading unchanged dependencies again. Resume does not install anything: it ensures the declared PostgreSQL, API and Vite services are running without restarting healthy services. Services are supervised independently of the agent process. Run `amp orb services ensure` again to recover stopped services; inspect failures with `amp orb service logs api`, `web` or `postgres`.

Open the **Richtfest** portal and choose the seeded Andreas or Luca identity on the development sign-in screen. Vite proxies API requests on the same origin; the API's authentication origin comes from the web service's current portal URL, not a committed hostname. The service manifest keeps development authentication enabled, email delivery disabled and the supervisor off. Setup does not copy credentials, customer sources, or login sessions into the snapshot. Provider execution still requires explicitly configured credentials and models.

From the repository root, run `bun run typecheck`, `bun test`, and `bun run build`. The generated `.env` sets both `DATABASE_URL` and `MASTRA_TEST_DATABASE_URL` to the disposable local database, so database-backed tests run rather than silently skipping. PDF extraction uses the installed language models through ignored links in `tools/reference-extraction/models`; it does not download customer files or run extraction during setup. Build the docs with `bun run --filter '@richtfest/docs' build` when a static docs export is needed; application builds and test suites are intentionally not part of every setup.

Generated `.amp/portals` links, `.env`, database files, uploads, and dependencies stay out of Git. Lifecycle changes must reach the project's default branch before future orbs can use them. Committing or testing these files locally does not deploy or change Railway.

### Seed a project for portal testing

After starting the local services, run `bun run db:seed:demo` from the repository root. It reuses the development identity seed and adds **DEMO · Wohnhaus Lindenhof** to Alpha. Sign in as Andreas or Luca in the Richtfest portal.

The project contains three labeled threads:

- **01 · Konzept und Quellen:** a formatted German concept in two revisions, with named citations and downloadable PDFs. Two source documents include three real PDF files: the original project brief, its changed revision (eight → six apartments), and a component overview with Unicode/acoustic symbols. Open an attachment to compare artifact revisions or follow a citation to its exact source version.
- **02 · Tokenlimit – Entscheidung testen:** a simulated failed source-reviewer run with three recorded attempts and the Yes / No / Describe decision. Yes uses the real permission-checked local preset update; it does not start an agent run.
- **03 · Zeichenlimit – kein Tokenproblem:** a simulated 10,000-character summary failure, deliberately without a token-increase offer.

These are synthetic records, not live model results, engineering requirements or approved findings. The command writes PDF bytes through the local storage adapter, makes no provider calls, and refuses production mode, non-loopback databases, database host overrides and bucket storage. All runs are terminal; the orb's supervisor remains disabled. Provider credentials are still required for new agent replies.

Stable IDs make repeat seeding non-destructive: it fills missing fixture rows without duplicating the project or replacing edits, approvals, messages or model settings. It snapshots the existing OpenAI/Medium preset and never changes it. After testing Yes, re-seeding does not reset that limit or the failed run's snapshot; use Agent model settings to restore the source reviewer's original limit if you want to repeat that decision. The command prints the three thread paths. Use the same root `.env` and `FILE_STORAGE_PATH` as the API so PDF downloads resolve.

## Hosting shape

The selected Railway project is `richtfest-os`, with `richtfest-monorepo` serving API and web on one origin, a separate `Postgres` service and the private `richtfest-files` bucket, all in EU West (Amsterdam). Connect through Railway's private `DATABASE_URL` reference. AWS and Neon are not part of this architecture.

The project is defined in `.railway/railway.ts` (Railway Infrastructure as Code); `railway.json` is deprecated and not read by new services. Railway evaluates the file only through `railway config plan` and `railway config apply`, not on deploy. Change services, variables or resources in that file and apply it; dashboard edits drift from it. A resource omitted from the file is deleted on the next apply, so always review the plan. Secrets stay `preserve()` in the file and are set with `railway variables`. The README lists the first-time setup commands.

Do not create the services through the dashboard's GitHub import. It detects the Bun workspaces and stages one service per package, and each of those builds fails because the packages are not standalone deployables.

Fumadocs exports a static site. The API serves its output under `/docs` behind sign-in, including document data and assets. No separate production Next.js server is required.

The public marketing page is the static `richtfest-landing` directory. The API serves it at `/landing/` on the Railway preview hostname and at `/` for `richtfest.ai`, `richtfest.andreaswissel.com`, `richtfest.si` and `www.richtfest.si`; the app remains at `/` on its Railway and app hostnames, including `app.richtfest.ai` and `richtfest-app.andreaswissel.com`. The Docker runtime includes the landing files alongside the web bundle.

Docker runs the typecheck, web build and docs export in independent stages, so Railway can build them in parallel and reuse unchanged stages. Only application source and build inputs invalidate these stages, not agent rules or infrastructure metadata. The runtime image installs production dependencies and only native bindings for its own architecture. All workspace typechecks still gate the image. The service pins `PORT=3000`, matching the public domain's target port.

The base image comes from Google's public Docker Hub mirror, pinned to the identical upstream Bun 1.3.8 multi-architecture digest, to avoid Docker Hub rate limits on shared builders. Application hosting and storage remain on Railway.

## Configuration before a live release

Configure the database connection, canonical HTTPS origin, authentication secrets, allowed origin and passkey relying-party settings, server-side credential encryption, Resend API key and verified sender. Follow the repository environment example for the exact variable names.

Choose the canonical origin before enrolling production passkeys. Keep local/test identities and preview mail delivery out of production. Missing delivery or provider configuration must remain explicit.

### Project address search

Set `GEOAPIFY_API_KEY` on the API service to enable project address autocomplete. Keep it server-side, never in a `VITE_` variable or source control. The Railway declaration preserves the secret; preparing the declaration does not configure an account, apply infrastructure or deploy. Without a key, the selector reports that search is unconfigured and still accepts manual addresses.

Authenticated users with project write permission can search through `/api/projects/address-suggestions`. Queries start after three characters and a short typing pause. Search text is sent to Geoapify, with Germany as a ranking bias and the user's English/German language; project IDs, names and customer records are not sent. Set usage limits appropriate to the account. The server bounds request time and response size, and hides upstream error bodies and credentials. Selected coordinates, provider IDs and data-source attribution are stored in Postgres; they are unreviewed search metadata, not survey evidence. The editor continues to resolve exact Berlin addresses through the official register rather than substituting search coordinates.

## Social link previews

The web HTML includes Open Graph and large-image Twitter card metadata, so crawlers do not need JavaScript or a session. In production, the API resolves preview URLs against the origin in `BETTER_AUTH_URL` at startup; set it to the public HTTPS origin, not a private Railway hostname. The image is the public, bundled 1200 × 630 JPEG at `/social-preview-v1.jpg`, not a private Bucket upload.

App links use the same Richtfest title, description and image. Preview metadata never includes project names, document content or authentication tokens. Docs remain behind sign-in and are not a public preview surface. When replacing the image, version its filename and update the HTML metadata to avoid stale image caches. Messaging services may retain previews of links already posted; existing messages are not automatically refreshed by a deployment.

Run `bun test tests/social-preview.test.ts` to build the web bundle and verify unauthenticated crawler responses and image delivery through the production API without a database connection.

## File storage

Use a private Railway Bucket for original uploaded files and revisions. Stream or upload directly to the bucket; the prototype does not impose an arbitrary application-level file-size cap. Platform and transport failures must still be handled explicitly. A local storage adapter is for development, and a service's temporary filesystem is not a production file store.

Configure bucket credentials and browser CORS for the application origin. For signed browser uploads, allow the exact HTTPS app origin, `PUT`, and the `Content-Type` request header; keep the bucket private and do not use a wildcard origin. The bucket responds to preflight requests based on this rule. Authorize access before creating short-lived upload or download URLs, and retain immutable object/version references in Postgres. Back up the database and bucket objects as a coherent recovery set, protect backup access and encryption keys, and test restoration in an isolated environment. See [Railway's upload and CORS guidance](https://docs.railway.com/storage-buckets/uploading-serving) for configuring its S3-compatible bucket API.

## First customer pilot preflight

Create the first real workspace administrator through an explicit production bootstrap before inviting customer users. Local seed identities and development sign-in helpers are test fixtures and must not be used to establish production access.

In the production service's shell, run `bun run auth:bootstrap-admin 'email@example.com' 'Administrator name' 'Workspace name'` from `/app/richtfest-os/apps/api`. This operator-only command requires an empty workspace, creates matching OS/auth identities and an Admin invitation with every current permission, and records a system audit event. It does not send email or mark email verified. The administrator requests a sign-in link from the public sign-in page and proves email ownership to accept the invitation. The invitation expires after seven days. After the first account exists, use Team invitations instead; the bootstrap refuses to change an existing workspace.

Before running an agent, the administrator selects the workspace provider in Settings, configures the model IDs for each enabled effort level, and saves a workspace credential or confirms that the pilot user has a personal credential. For Vercel AI Gateway, use `provider/model` model IDs. Verify provider selection and readiness without sending a paid request, then use the intended Railway deployment to run the first credited call.

Complete the pilot with a real project source: upload the original file, start the project conversation, inspect the agent's source references, and publish only the reviewed artifact revision. This walkthrough checks the customer workflow and its audit trail rather than treating a successful provider response as completion.

## Release procedure

Preparing configuration does not authorize deployment. On an explicit deploy request, follow `AGENTS.md`: review the intended changes, update release notes and affected docs, run required checks, commit on local `main`, then push that branch to `origin/main`.

Before that commit and docs build, move the included `Unreleased` entries into the deployment's `## YYYY-MM-DD` section in Europe/Berlin time. Reuse an existing section for that day and leave only genuinely undeployed work in `Unreleased`. See [Writing documentation and release notes](/docs/engineering/writing-docs#preparing-a-release) for the release-note lifecycle and historical corrections.

After the push, watch the Railway deployment for that commit. If the build or deploy fails, read the logs, fix the cause and push again straight away. Report included database migrations.

### Updates in open tabs

When a different web build is available, signed-in users see **New updates available** at the bottom of the desktop navigation rail, just above their profile. Save any unsaved work, then click the button to reload the current page. The app never reloads automatically on deployment or navigation.

The web build writes the same asset-filename fingerprint to an HTML meta tag and `version.json`. Open tabs compare their loaded fingerprint with `/version.json` once a minute while visible and whenever the tab becomes active. The API serves the version file and app HTML with `Cache-Control: no-store`; version checks are not persisted in the workspace query cache. Failed or malformed checks do not announce an update. Vite development has no build marker and does not poll.

An existing tab must have loaded a build containing this feature to detect subsequent updates. Redeploying the same web assets does not trigger the button; no extra Railway variable or database migration is required.

### Recovering an older open tab

Open tabs can still request hashed JavaScript, CSS and other build assets from an earlier deployment. Before accepting traffic, production startup retains the current `dist/assets` files in the existing private Railway Bucket under `web-assets/v1/`. Existing filenames are reused; files are not automatically expired or deleted. Storage grows with distinct build assets, not with every restart. Bucket credentials are required: if retention fails, the new process refuses to listen, so Railway's healthcheck cannot promote an unarchived build. Development does not archive files or require bucket access.

The API serves current assets from the container first, without a storage request. Missing local assets fall back to the archive, streamed on the same origin with the correct MIME type and one-year immutable caching. The bucket stays private. Only flat, hashed build filenames with allowed asset extensions are exposed; the fallback cannot access customer object keys, source maps, HTML or manifests. No browser CORS or new service is needed. Unknown `/assets/` files return a non-cacheable, non-HTML 404; a storage outage returns a non-cacheable 503 instead of pretending the file is missing.

Retention protects builds archived after this feature is installed; it cannot recover files already removed by earlier deployments. Those tabs may still need one reload. Asset retention also does not make incompatible API changes safe: keep API contracts backward-compatible for open clients.

A network interruption or JavaScript initialization error can still prevent loading. The account-security recovery notice does not claim an update was definitely responsible; the browser console logs the original authentication-module error and the tab's build fingerprint, without sending account data to a telemetry service. Use the Network panel's asset URL/status and this underlying error to distinguish a missing download from an initialization bug.

OpenUI and Markdown loads have local error boundaries. A missing renderer shows a translated reload prompt in place of that content, without unmounting the surrounding conversation or composer. Markdown falls back to its original plain text. Copy unsent text or unsaved changes before choosing **Reload app**; confirmation is required, and cancellation leaves the page untouched. There is no automatic reload or retry loop. A confirmed reload keeps the current URL and fetches the current app; it cannot repair an ongoing outage.

Lazy project and Help routes have eagerly available error and initial-loading elements so failed imports remain visible inside the shell, including on a direct page load. Ordinary rendering errors use a separate generic error message rather than being misidentified as a stale deployment. Recovery cannot run if the initial application bundle itself fails to load, and tabs opened before this behavior was deployed need a manual refresh once.

To verify locally, build the web app and block its hashed OpenUI or Help module in browser network interception. Check that the conversation/composer or navigation shell remains, cancel the reload confirmation, then unblock the module and confirm reload. The browser regression checks can also be run on Vite with `import('/tests/module-recovery.browser.tsx').then(m => m.testModuleRecovery())`.

Run `bun test richtfest-os/apps/api/src/web-assets.test.ts tests/social-preview.test.ts` to check archive retention across replacement builds, private-object isolation, outage behavior, cache headers and current HTML/version responses. The archive test uses an isolated loopback S3 fixture, never production storage. For browser verification, leave a built app tab open before visiting Account settings, replace the served build, then open Account settings: the old authentication module should return 200 through the archive and the tab should not reload.

## Docs build

Run `bun run --filter '@richtfest/docs' build`. The generated `out` directory belongs to the deploy artifact. The production API must apply its session/access guard before serving the entire docs directory.

See [Railway Storage Buckets](https://docs.railway.com/storage-buckets) for the selected file storage service.

The implementation follows the [Fumadocs Next.js guide](https://www.fumadocs.dev/docs/manual-installation/next) and [static export guide](https://www.fumadocs.dev/docs/deploying/static).
