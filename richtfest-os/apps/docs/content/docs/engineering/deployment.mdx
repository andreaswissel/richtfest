## Hosting shape

The selected Railway project is `richtfest-os`, with `richtfest-monorepo` serving API and web on one origin, a separate `Postgres` service and the private `richtfest-files` bucket, all in EU West (Amsterdam). Connect through Railway's private `DATABASE_URL` reference. AWS and Neon are not part of this architecture.

The project is defined in `.railway/railway.ts` (Railway Infrastructure as Code); `railway.json` is deprecated and not read by new services. Railway evaluates the file only through `railway config plan` and `railway config apply`, not on deploy. Change services, variables or resources in that file and apply it; dashboard edits drift from it. A resource omitted from the file is deleted on the next apply, so always review the plan. Secrets stay `preserve()` in the file and are set with `railway variables`. The README lists the first-time setup commands.

Do not create the services through the dashboard's GitHub import. It detects the Bun workspaces and stages one service per package, and each of those builds fails because the packages are not standalone deployables.

Fumadocs exports a static site. The API serves its output under `/docs` behind sign-in, including document data and assets. No separate production Next.js server is required.

The public marketing page is the static `richtfest-landing` directory. The API serves it at `/landing/` on the Railway preview hostname and at `/` for `richtfest.andreaswissel.com`, `richtfest.si` and `www.richtfest.si`; the app remains at `/` on its Railway and app hostnames, including `richtfest-app.andreaswissel.com`. The Docker runtime includes the landing files alongside the web bundle.

Docker runs the typecheck, web build and docs export in independent stages, so Railway can build them in parallel and reuse unchanged stages. Only application source and build inputs invalidate these stages, not agent rules or infrastructure metadata. The runtime image installs production dependencies and only native bindings for its own architecture. All workspace typechecks still gate the image. The service pins `PORT=3000`, matching the public domain's target port.

The base image comes from Google's public Docker Hub mirror, pinned to the identical upstream Bun 1.3.8 multi-architecture digest, to avoid Docker Hub rate limits on shared builders. Application hosting and storage remain on Railway.

## Configuration before a live release

Configure the database connection, canonical HTTPS origin, authentication secrets, allowed origin and passkey relying-party settings, server-side credential encryption, Resend API key and verified sender. Follow the repository environment example for the exact variable names.

Choose the canonical origin before enrolling production passkeys. Keep local/test identities and preview mail delivery out of production. Missing delivery or provider configuration must remain explicit.

## Social link previews

The web HTML includes Open Graph and large-image Twitter card metadata, so crawlers do not need JavaScript or a session. In production, the API resolves preview URLs against the origin in `BETTER_AUTH_URL` at startup; set it to the public HTTPS origin, not a private Railway hostname. The image is the public, bundled 1200 × 630 JPEG at `/social-preview-v1.jpg`, not a private Bucket upload.

App links use the same Richtfest title, description and image. Preview metadata never includes project names, document content or authentication tokens. Docs remain behind sign-in and are not a public preview surface. When replacing the image, version its filename and update the HTML metadata to avoid stale image caches. Messaging services may retain previews of links already posted; existing messages are not automatically refreshed by a deployment.

Run `bun test tests/social-preview.test.ts` to build the web bundle and verify unauthenticated crawler responses and image delivery through the production API without a database connection.

## File storage

Use a private Railway Bucket for original uploaded files and revisions. Stream or upload directly to the bucket; the prototype does not impose an arbitrary application-level file-size cap. Platform and transport failures must still be handled explicitly. A local storage adapter is for development, and a service's temporary filesystem is not a production file store.

Configure bucket credentials and browser CORS for the application origin. For signed browser uploads, allow the exact HTTPS app origin, `PUT`, and the `Content-Type` request header; keep the bucket private and do not use a wildcard origin. The bucket responds to preflight requests based on this rule. Authorize access before creating short-lived upload or download URLs, and retain immutable object/version references in Postgres. Back up the database and bucket objects as a coherent recovery set, protect backup access and encryption keys, and test restoration in an isolated environment. See [Railway's upload and CORS guidance](https://docs.railway.com/storage-buckets/uploading-serving) for configuring its S3-compatible bucket API.

## First customer pilot preflight

Create the first real workspace administrator through an explicit production bootstrap before inviting customer users. Local seed identities and development sign-in helpers are test fixtures and must not be used to establish production access.

In the production service's shell, run `bun run auth:bootstrap-admin 'email@example.com' 'Administrator name' 'Workspace name'` from `/app/richtfest-os/apps/api`. This operator-only command requires an empty workspace, creates matching OS/auth identities and an Admin invitation with every current permission, and records a system audit event. It does not send email or mark email verified. The administrator requests a sign-in link from the public sign-in page and proves email ownership to accept the invitation. The invitation expires after seven days. After the first account exists, use Team invitations instead; the bootstrap refuses to change an existing workspace.

Before running an agent, the administrator selects the workspace provider in Settings, configures the model IDs for each enabled effort level, and saves a workspace credential or confirms that the pilot user has a personal credential. For Vercel AI Gateway, use `provider/model` model IDs. Verify provider selection and readiness without sending a paid request, then use the intended Railway deployment to run the first credited call.

Complete the pilot with a real project source: upload the original file, start the project conversation, inspect the agent's source references, and publish only the reviewed artifact revision. This walkthrough checks the customer workflow and its audit trail rather than treating a successful provider response as completion.

## Release procedure

Preparing configuration does not authorize deployment. On an explicit deploy request, follow `AGENTS.md`: review the intended changes, update release notes and affected docs, run required checks, commit on local `main`, then push that branch to `origin/main`.

After the push, watch the Railway deployment for that commit. If the build or deploy fails, read the logs, fix the cause and push again straight away. Report included database migrations.

## Docs build

Run `bun run --filter '@richtfest/docs' build`. The generated `out` directory belongs to the deploy artifact. The production API must apply its session/access guard before serving the entire docs directory.

See [Railway Storage Buckets](https://docs.railway.com/storage-buckets) for the selected file storage service.

The implementation follows the [Fumadocs Next.js guide](https://www.fumadocs.dev/docs/manual-installation/next) and [static export guide](https://www.fumadocs.dev/docs/deploying/static).
