## Where information belongs

| Information | Location |
| --- | --- |
| Durable agent rules and project constraints | Root `AGENTS.md` |
| Detailed engineering conventions, design and performance budgets | Existing root convention documents |
| Current workflows, architecture and setup | These Fumadocs pages |
| Completed user-facing or operational changes | `CHANGELOG.md`: dated sections, written on the day the work is done |
| Raw meeting notes and project evidence | Their source/context records, not agent instructions |

## Writing a change

Update the page that already owns the topic instead of appending a parallel account. Rewrite outdated behavior, remove obsolete setup and use links when detail already exists elsewhere. Clearly identify decisions awaiting implementation; never describe a mocked or unconfigured integration as available.

Keep procedures concrete: who acts, what they do, what they should see and what remains to be configured. Do not include credentials, private customer files or copied transcripts in shipped docs.

Record meaningful completed, verified work in the root `CHANGELOG.md` as it happens, not only at deployment, directly under today's `## YYYY-MM-DD` section in Europe/Berlin time. Create the section at the top when it does not exist yet; there is no `Unreleased` section. Group rapid iterations into one concise item. The changelog records what changed; these docs explain how things work now.

## Preparing a release

Entries already sit under their date, so a same-day deployment needs no changelog step. If a deployment happens on a later day than the entries were written, move that deployment's entries to the deployment day's section in the deployment commit. Reuse an existing section for the same day instead of creating a duplicate; keep dated sections newest first. Keep unrelated, undeployed work and its notes on a separate branch, outside the deployment commit.

The production Docker build sets `REQUIRE_RELEASED_CHANGELOG=1` and fails if an `Unreleased` section with notes appears, so undated notes are never published. To check the release gate locally, run `REQUIRE_RELEASED_CHANGELOG=1 bun run --filter '@richtfest/docs' build`.

Confirm the Railway deployment succeeded before reporting the release as live. If deployment is abandoned, remove or redate only its still-undeployed entries. For a historical correction, check successful deployment records and the commits they contain; a commit date alone does not establish a release date. Do not relabel already shipped history with today's date.

## Before committing

Include the release note for a user-facing or operational change and any affected workflow, architecture or setup docs in the same commit as the change. Run `bun run --filter '@richtfest/docs' build` whenever changelog or docs content changes, and inspect the diff before staging only the files that belong to the change.

The Docs Changelog page is generated automatically from root `CHANGELOG.md` when Docs starts or builds, including the production Docker build. There is no second changelog to maintain or Git hook to install. The generated `content/docs/changelog.md` is ignored by Git; never edit or stage it. Restart the Docs development server after changelog edits to regenerate the page. The root heading is replaced by page metadata; release sections and entries are preserved.

## Verification

Build the docs and inspect the affected pages in the signed-in application. Check navigation, readability and links, and verify that signed-out visitors cannot fetch pages or their static data. Documentation changes ship with the behavior they describe.
