## Invitations and sign-in

The prototype uses invite-only membership. An administrator invites a person by name and email, assigns a workspace role and sets the invitation expiry; pending invitations show the person's name and email. A time-limited, single-use magic link verifies first access. Resend is the selected delivery provider. An unconfigured delivery service must not report that it sent an email.

Sign-in emails use a lightweight Richtfest-branded layout with a sign-in button, a copyable fallback link and a plain-text alternative. The sender must be an email address on a verified Resend domain; the default Resend sender is limited to testing with the Resend account owner's address. A configured status on the sign-in page confirms the environment variables are present, not that a particular message has been delivered.

After first access, a person can enroll a password or passkey for subsequent sign-in. Enrollment belongs to that verified account and requires an authenticated, appropriately verified session. Google sign-in is a later extension, not a prerequisite for this prototype.

Email-link sign-in is the primary login path. Password sign-in and an explicit passkey action remain available as secondary options. On browsers that confirm WebAuthn conditional mediation, the login email field can offer a saved passkey through the browser's own credential UI; Richtfest does not enumerate or report which passkeys exist.

Local development can enable **Local development access** for seeded `@richtfest.local` identities by setting `ALLOW_DEV_AUTH=true`. The server only creates development sessions for those seeded identities with one active workspace membership. This shortcut is opt-in for non-production environments and is always disabled when `NODE_ENV=production`; shared development environments should use synthetic data only.

If an open tab cannot load the sign-in code after a deployment or network failure, use **Reload app** and try again. The app does not automatically reload or resend a sign-in request.

Roles control application permissions. Removing access must revoke active sessions and outstanding invitations. Authentication establishes identity; business routes still enforce workspace scope and capability checks.

## Roles and permissions

Open **Team → Roles and permissions** to create a workspace role or edit its name, description and permissions. Assign roles through **Manage member**, or choose one when creating an invitation. Existing roles and assignments are unchanged until you save a change.

All roles created or saved here retain **Use Richtfest OS**. Select view and edit permissions for CRM, projects and knowledge separately; editing does not automatically grant viewing. Knowledge approval and agent execution are separate capabilities. For example, a project reader needs **Use Richtfest OS** and **View projects**, without **Edit projects**.

**Manage workspace access** (`access:manage`) grants administration of invitations, member assignments and roles, as well as shared settings that already use this permission. It is powerful administrative access, not limited to managing one role. Management depends on this permission, not the role's name; Admin is simply the default fully permitted role.

Saving permissions affects every member assigned that role. The server reads current grants on each request, so removing a grant blocks subsequent protected requests without requiring a new sign-in. Already loaded content is not erased from another person's open tab. Use offboarding to revoke workspace membership, sessions and pending invitations.

At least one active member must retain both OS access and workspace access management. Role edits, member reassignment and offboarding are checked transactionally, including concurrent changes, to prevent administrator lockout. Role creation and edits are recorded in the audit log; edits include the previous and new permissions. Roles are workspace-scoped and cannot be assigned or edited across workspaces.

## Account settings

Open your name in the sidebar to reach Account settings. The Preferences section contains language (English or German), display density (Dense or Normal) and appearance (Light or Dark); changes are saved to your account and restored when you return. Passwords, passkeys and active sessions are managed on the same page.

Password status remains available even when an older session can no longer list active sessions. In that case, the Active sessions section asks you to sign in again instead of reporting a connection failure. To set your first password, sign in using a fresh email link and open Account settings within 15 minutes; an already-configured password is shown as configured rather than prompting you to enroll again.

If security details cannot load, use **Try again** to fetch them without resubmitting any changes. If the sign-in code itself is unavailable, use **Reload app** instead. A failed passkey lookup is not shown as an empty list, and security actions that need unavailable data or code remain disabled until recovery.

The Settings area is split into navigable sections: AI connections (`/settings`), agent model settings (`/settings/models`), agent profiles (`/settings/agents`) and account settings (`/settings/security`). The section links appear below each Settings page title.

## AI connections

OpenAI, Anthropic and Vercel AI Gateway are supported connection choices. The workspace selects one active provider; when no setting exists, OpenAI remains the default. Live provider execution remains unconfigured until an execution adapter, credential and effort preset are available.

Each provider has two credential scopes:

| Scope | Managed by | Used for |
| --- | --- | --- |
| Workspace | Workspace administrator | Shared fallback for permitted workspace work |
| Personal | The individual user | That user's work with the selected provider |

For the active provider, use the personal key when present, otherwise its workspace key. Do not silently switch providers. Show the effective scope without revealing the secret. Vercel uses an encrypted AI Gateway key from Railway or another external runtime at `https://ai-gateway.vercel.sh/v1`; gateway model IDs use `provider/model` form and gateway failures never fall back to a direct provider.

Store credentials encrypted on the server. Never return saved keys to the browser or include them in logs or audit records. If encryption is unavailable, saving secrets must fail with an actionable setup state.

A saved key does not prove that it is valid, funded or executable. Connection configuration and execution readiness must be displayed separately.
