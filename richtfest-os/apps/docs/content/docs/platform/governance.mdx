## An accountable work record

The governance contract preserves the assigned request, source IDs and versions, initiating user, executing actor, tool actions and safe result summaries. Record relevant policy checks, approval decisions, outcome and errors with a stable run or correlation ID.

A concise decision rationale should explain the evidence and criteria supporting an action. Hidden model reasoning is not an audit artifact. Do not store credentials, authentication tokens or unnecessary private content in event metadata.

The model proposing a tool call does not authorize it. The platform checks the current actor, workspace and capability before executing. Consequential external actions require the appropriate human approval.

Provider output is constrained to a small allowlist: exact project-source reads, proposed drafts, missing-input questions and one bounded source-review delegation. A specialist child run has its own task, source scope, status and output, and cannot delegate again. Unknown tools and invented source or artifact references are rejected.

OpenUI uses a generated registry shared by the provider prompt, server parser and web renderer. Generated UI can display only registered Richtfest components. Query, mutation, dynamic action, external URL and executable markup paths are disabled. Model-generated status UI is always presented as proposed; approval comes from the review record.

## Workspace role guidance

Administrators with both `knowledge:read` and `access:manage` can configure the existing supervisor and reviewer profiles in Settings → Agents. Changes are workspace-scoped and audited; only approved company-wide knowledge can be assigned. Routing phrases influence planning as hints and confer no authority. Each durable supervisor run preserves its own configuration and reference-content snapshot. See [Agent profiles](/docs/architecture/agent-runtime#agent-profiles) for configuration and the fixed safety boundaries.

## Review company knowledge

Open **Company knowledge** in the navigation to browse shared, company-wide entries or ask a question in the top composer. The library defaults to **All** review statuses; switch to **Approved** or **Awaiting review**, or filter by original or display title. Lists are paginated with 25 entries per page. Project-specific knowledge remains in its project's Knowledge view. Pending-review links on the overview open the corresponding company entry or project knowledge view.

The category rail (a selector on narrow screens) scopes both the list and new conversations. Existing entries start **Unfiled**. Users with `knowledge:write` can create and rename one-level categories and move selected entries, including back to Unfiled. Category names are unique within the workspace, ignoring case. Selection is limited to the current page and clears when filters or pages change or a chat starts. Actions float above the bottom of the list without shifting its rows. Moves are atomic and audited; they do not change content, approval or agent-profile assignments. Categories are organization, not separate access boundaries.

Display titles, sources and chapters are separate library metadata. The compact list shows source and chapter beneath the title, with category and review status alongside. Original titles remain visible on entry detail pages; content, provenance and approval are not rewritten when metadata changes. The controlled Baukosten training-import organization command recognizes its import marker and known title convention, fills only wholly unorganized entries and leaves unknown formats or existing organization untouched. It assigns domain categories, plus Fallstudien, Glossar, Orientierung and Qualität und Quellen. It does not guess categories for other corpora.

Open an entry to read its full formatted content, source references and caveats. Entries have stable links that can be shared with colleagues in the same workspace. Company imports may contain filenames and checksums in their text; those references are not uploaded originals or linked file revisions. Check the underlying evidence before approval.

After reading, choose **Approve knowledge** and confirm. For several entries, select their checkboxes and choose **Approve selected** in the floating bar. The confirmation lists only selected entries still awaiting review, with links to open their content in a new tab. Cancel makes no changes. Bulk approval is atomic, workspace/company-scoped and records the reviewer, time and an audit event for each newly approved entry; already approved entries keep their original approval. Reading requires `knowledge:read`; approval requires `knowledge:approve`, independently of category-edit permission. Approval makes entries eligible for explicit assignment under Settings → Agents and approved-only search by project agents; it neither assigns them automatically nor certifies an engineering calculation. Importing, opening or selecting entries never approves them.

## Ask company knowledge

Submit a natural-language question in the top composer to transition immediately into a chat. Follow-up questions stay in that conversation's original category and review status; return to the library to change scope or begin a new conversation. Enter submits; Shift+Enter adds a line. Execution requires `knowledge:read`, `agent:run`, a configured active provider connection and its low-complexity supervisor preset. It uses the explicit workspace provider selection and that provider's personal credential before its workspace credential. Without a connection or preset, search is unavailable rather than simulated.

The model expands the question into up to eight German/English terms. PostgreSQL full-text search retrieves at most eight company entries from this workspace; project knowledge is excluded. Each entry supplies at most 4,000 characters of matching source windows. A second tool-free model call answers only from those excerpts. Each call is capped at the lower of the configured preset limit and 2,500 output tokens. This is bounded retrieval, not an exhaustive document review or a deterministic calculation.

Answers display linked source excerpts and their review status at search time. The server rejects unknown entry IDs and quotes that are not exact substrings of the supplied source windows. Exact quotes verify provenance, not the correctness of the model's interpretation or whether they support every claim. Check current content and caveats before use. Broaden filters or rephrase when no supported answer is found.

Questions, parent turns, filters, answers, source-body hashes, citation snapshots, usage and execution status are persisted in Postgres. The ten most recent conversation leaves are private to the initiating user within the workspace, not shared project conversations. Each conversation supports up to 20 turns. Up to six prior turns and 12,000 characters help resolve follow-up references, but previous answers are never evidence: every new answer must cite newly retrieved source windows. Only the latest completed or failed turn can receive a follow-up; running or interrupted conversations require waiting or a new conversation. Search start and completion/failure are audited. Failed or interrupted calls are not automatically retried; running records older than three minutes appear interrupted until a terminal result arrives. A new search is an explicit new provider request. Neither search nor category changes approve knowledge or assign it to agent profiles.

### Controlled import organization

After applying migration `0035_company_knowledge_conversations`, operators can preview known import organization from the API directory:

```sh
bun src/scripts/organize-company-knowledge.ts <tenant-uuid> <member-uuid>
```

The supplied active member must have `knowledge:read` and `knowledge:write`. Review the returned proposals before repeating with `--apply`. Applying is an explicit database write, not part of startup or migration; obtain production-write approval first. It is transactional and audited, preserves all original fields and existing organization, and produces no further changes on repeat execution. The script does not import original files, approve content or assign profiles.

Project-agent **`search_company_knowledge`** is a separate workflow: it always excludes drafts and project-specific entries, uses deterministic retrieval without extra AI search calls, and saves evidence in the requesting run's audited steps rather than this private search history. Retrieved guidance remains separate from project-file evidence and engineering validation. See [Agent profiles and retrieval](/docs/architecture/agent-runtime#agent-profiles) for limits and retry behavior.

## Activity without clutter

Contextual activity is a filtered view of the audit record. A project shows relevant project events; a knowledge item shows its drafting and review history. Broader audit inspection supports filtering and pagination for permitted users.

An event can be important for auditing without being useful in every screen's activity feed. Filtering presentation must not discard the underlying record or bypass access checks.

## Processing and recovery

Long-running work needs durable status: queued, running, requiring review, failed or finished as applicable. Provider summary text streams into a stable run turn while bounded checkpoints preserve progress for reloads and interruptions. Stopping a run aborts the active request when possible and prevents late output from being committed. Preserve actionable failure information and the relationship to the source input. Offer retries only for implemented operations, and make repeated processing safe.

Providers and tools that have not been enabled must remain visibly unavailable. Do not populate success histories with simulated agent execution.
