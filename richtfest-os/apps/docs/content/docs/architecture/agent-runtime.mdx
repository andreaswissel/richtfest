## Gated V1

Project chat is the entry point for agentic work. The Richtfest OS host authenticates the actor, applies workspace and role access, and passes the approved context to a Mastra supervisor. Context includes a bounded inventory of the project's latest ready file versions so the planner can select relevant exact versions even when the user has not attached them. Inventory metadata is discovery-only; specialists resolve assigned versions into bounded excerpts before they can support citations. The supervisor interprets the request, creates bounded assignments and performs an integration review. When enabled in the model preset, a separate independent-review phase re-resolves the assigned immutable sources and checks the proposed result before the draft is saved. A human can steer, approve or cancel the run at the review boundary.

The enabled V1 delegates to the `source_reviewer` and `requirements_reviewer` roles. Their assignments are bounded by exact versions in the project inventory or explicitly attached to the run, and return structured summaries, rationale and citations. A specialist receives only readable excerpts, identified by their exact immutable version IDs; file IDs and unreadable source IDs are not citation targets. Unreadable files remain named coverage gaps, and truncated excerpts must be reported as limited evidence. The server still rejects citations outside the assigned readable versions. The optional `independent_reviewer` role receives a fresh review request and re-resolved source excerpts; it can request bounded revisions but cannot approve the result. Uploaded files remain unreviewed evidence until a person reviews them; that status does not prevent an agent from reading them. Calculation specialists and deterministic calculation tools are future work; no engineering calculation is performed by this workflow.

## Delegation shape

The supervisor owns coordination and revision. It delegates focused source extraction and requirements structuring, then reviews the returned evidence. Presets may enable an additional independent-review provider call; the default remains off to preserve existing behavior and avoid adding cost without workspace choice. That review receives the original goal, specialist results, the supervisor's proposed result, and freshly resolved source excerpts. The calculation branch shown in the diagram is a future domain capability and is unavailable in V1. Any eventual deterministic calculation tool remains versioned and requires explicit review before consequential use.

Mastra workflow checkpoints and workflow run IDs use the Mastra Postgres store. Richtfest domain Postgres records hold conversations, assignments, tasks, evidence links, approvals, events and the policy snapshot. Lease state, replica coordination through Postgres advisory locks, row locks and generation fences make cancellation, restart and resume durable; restart and generation-fencing behavior is covered by the runtime tests. Project source files and revisions remain in private Railway Buckets, while Postgres stores their metadata and references.

The enabled supervisor worker polls queued runs and advances them through the persisted Mastra workflow runtime. Each run uses a Postgres advisory lock while its checkpoint is read or written, so multiple service replicas can share the queue without advancing the same generation concurrently. Mastra storage keeps workflow checkpoints and run IDs; the Richtfest records remain the source of truth for phase state, assignments, evidence and review outcomes. A queued run therefore remains queued until a worker claims it, then moves through the same durable runtime used for restart and resume.

## Review and control

The supervisor may propose a plan and ask specialists to work, but it does not silently approve consequential outcomes. Project participants can steer a queued or running run, revising its direction; steering cancels its current specialist assignments and starts a new planning generation. A message sent after a run has finished starts a new run. Participants can also cancel active work. Results should remain attributable to the assignment and source evidence that produced them. Unconfigured providers, tools or external actions stay explicit in the UI.

Each completed supervisor review saves a draft artifact and immutable revision alongside the assistant response. The conversation displays a registered OpenUI PDF attachment for that exact revision, with a download action; the artifact can also be opened for review. PDF generation reads the saved revision and does not approve or publish it. Reviewing the supervisor run and approving the artifact are separate actions; completion does not publish reviewed knowledge. A follow-up result creates a new draft, while retrying the same completed generation reuses its saved result.

Transient provider timeouts, rate limits, service errors and invalid structured model responses are retried with up to three attempts. Provider cooldowns are honored up to five minutes; longer cooldowns stop automatic recovery without sending an early request. Without a provider cooldown, rate limits wait five and ten seconds, while other transient failures use short backoff. Permission and configuration errors are not retried automatically. Live summaries restart cleanly for each attempt. If a run still fails, the conversation shows a terminal outcome in chronological order with the recorded safe reason, run details and a manual retry action. Provider exception text is not persisted because it can contain credentials or request data.

The project workspace keeps the main conversation focused on the request and result. Its Subagents panel lists each specialist by a readable name and status; prior cancelled work is collapsed. Open a row to inspect that specialist's dedicated, read-only thread with its assignment, result and source links. These threads use the durable run and activity records, not a second editable conversation. Return to the main conversation to steer the coordinator. The coordinator's latest result exposes the explicit review action, while specialist threads cannot independently approve, retry or cancel managed work. Shared work provides a compact list of conversations and agent assignments. Conversation links open the main workspace, and each conversation retains an Add task action. Agent results and lifecycle controls are available on demand; specialist rows link to their read-only threads. Provider configuration stays in Settings; the work list only calls out unavailable execution when action is needed.

Project agent lists separate active runs from done runs. They show live elapsed runtime, reported token usage and an approximate cost when the model's pricing is known. Runtime displays seconds for the first five minutes, then whole minutes. Usage is recorded from provider-reported input, output, reasoning and cached-token counts; cost estimates use the configured model pricing snapshot and are omitted when a rate is unavailable.

## Supervisor presets

Workspace administrators can configure a provider's `Low`, `Medium`, `High` and `Ultra` presets. Each preset names the supervisor model and bounded reasoning effort, then sets independent model and effort values for the source and requirements specialists. Limits for parallel specialists, total assignments and supervisor revisions are stored with the preset. The selected preset is resolved when a run starts and its policy is snapshotted with the durable run record, so later configuration changes do not rewrite history.

For OpenAI and Anthropic, the model fields in Settings use the connected provider credential to load the account's available model catalog. Credentials remain server-side; Settings shows a masked placeholder for a saved key and never returns its secret value. GPT 6 models and Claude Opus 5.5 / Sonnet 5.5 models are grouped first; other models returned by the provider remain selectable. Existing model IDs are retained in the selector if they are no longer returned by the catalog. Vercel AI Gateway model IDs remain manually configured because its public catalog does not indicate which models an account can use.

The workspace provider setting selects the active provider for direct and supervisor execution. Empty model IDs leave Anthropic and Vercel presets unconfigured; OpenAI retains its `gpt-4.1-mini` direct default when no model environment value is supplied. The UI does not invent or silently switch providers. Vercel presets use `provider/model` Gateway IDs at `https://ai-gateway.vercel.sh/v1` and do not fall back to OpenAI or Anthropic on a gateway failure. Vendor defaults can be restored by an administrator through Settings.

## Agent profiles

Settings → Agents configures the workspace profiles: Supervisor (`supervisor`), Source reviewer (`source_reviewer`), Requirements reviewer (`requirements_reviewer`) and Independent reviewer (`independent_reviewer`). Users with both `knowledge:read` and `access:manage` can save plain-language role instructions, routing phrases and assigned knowledge. These controls customize the existing team; they do not create new roles or grant permissions. Agent model settings control whether the independent-review pass runs for a preset; legacy and vendor presets default to off.

Use instructions for working preferences within a role, such as checking dimensions before summarizing a source. Routing phrases are optional hints the supervisor considers while planning assignments, not guaranteed triggers. Assign only approved company-wide knowledge: project-specific or unapproved drafts cannot be selected. Company references guide the work but do not replace the project's source evidence or supply project-version citations.

Each new durable supervisor run saves the profile versions, instructions, routing phrases and assigned reference content in its own snapshot. Planning, specialist work and review use that snapshot, so later settings or knowledge edits do not rewrite the run's context. Existing runs without a profile snapshot retain the original defaults.

Workspace instructions remain subordinate to the platform safety and output contract. They cannot expand source access, change supported roles, bypass human review, approve an output, authorize external actions or relax structured output and citation validation. Engineering calculations remain unavailable until a validated deterministic tool exists.

## Runtime setup

The supervisor worker is disabled by default in local development and enabled in production with `AGENT_SUPERVISOR_ENABLED=true`. Before enabling it in a new environment, apply the standard application migrations and configure model presets. The application migration provisions the Mastra workflow checkpoint schema in `rf_agent_runtime` and copies compatible snapshots from the former runtime schema when present. The planner routes file-based work to source and requirements reviewers. Project files are readable as unreviewed evidence; human review applies to the proposed result. If a user explicitly asks to review every project source, assignments cover the available inventory or report the coverage limit.

For a new environment, apply the standard application migrations first, configure model presets, and only then enable the worker:

```sh
bun run --filter '@richtfest/api' db:migrate
AGENT_SUPERVISOR_ENABLED=true bun run --filter '@richtfest/api' dev
```

The application starts the worker with automatic Mastra store initialization disabled, so `db:migrate` must complete before queued runs can be claimed. The `db:migrate-agent-runtime` script remains available for explicit full-store setup, but it is not required for the supervisor workflow checkpoint tables. When enabled, the worker logs its startup, polling failures and per-run execution failures with the run ID and generation; repeated errors are rate-limited to keep the API log useful.

The enablement flag only turns on the worker. A workspace administrator must configure a valid model ID and bounded preset values for the selected provider and effort in Settings before starting a run. Vendor model environment variables may provide defaults, but Richtfest does not automatically choose a frontier model, infer a paid model or treat a provider API key as a complete preset. Anthropic presets omit reasoning effort because that adapter does not accept the field.

The runtime policy snapshot answers which supervisor and specialist models, limits, independent-review setting and preset version governed a run. Domain records answer what the specialists found, which source revisions support it, what the independent reviewer flagged and whether a person approved it. These are separate records: a valid runtime snapshot does not make a calculation tool available, approve a result or certify engineering or regulatory compliance.

The runtime verification uses synthetic Mastra/provider fixtures and Postgres restart and fencing tests. It does not claim a live provider execution or a completed calculation workflow.

## Text equivalent of the diagram

1. Project chat sends a prompt and project context to OS authentication and access checks.
2. The Mastra supervisor receives the authorized context and routes durable assignments to `source_reviewer` and `requirements_reviewer`.
3. Those two specialists perform bounded work and return structured results with evidence.
4. The supervisor integrates and reviews the result set. If the preset enables independent review, a fresh reviewer pass re-reads assigned sources and can request bounded revisions. A human may steer, approve or cancel. Calculation work is unavailable in V1 and remains a future capability.
5. Mastra Postgres stores workflow checkpoints and run IDs; Richtfest Postgres stores conversations, tasks, evidence, events, approvals and policy snapshots. Private Railway Buckets store source files and revisions.
