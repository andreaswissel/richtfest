## Gated V1

Project chat is the entry point for agentic work. The Richtfest OS host authenticates the actor and applies workspace and role access. The composer defaults to **Suggest**, with explicit **Chat**, **Team** and **Report** overrides independent of provider and effort. Suggest checks the mode on submission; it can proceed only with Chat without additional confirmation. Chat retrieves sources and company knowledge but cannot delegate or create artifact drafts. Team delegates bounded specialist work and returns findings in chat without forcing an acoustic report. Report needs a goal, not a composer template selection or attached sources. The API infers the built-in interior-noise or exterior-noise concept format from the goal, falling back to sound-insulation review. Without explicit attachments, it snapshots the latest ready project-evidence versions, up to 100, rejecting an empty or truncated inventory. Explicit exact eligible attachments still scope the evidence. The planner must cover every selected version; source, citation, review and approval checks remain enforced. Team and Report require the supervisor feature to be enabled.

The selected workflow is saved in the run's existing `modelPolicy.workflow` JSON snapshot and retained by retries and fresh reruns; no schema migration is needed. Historical runs and API callers omitting `workflow` retain their previous orchestration behavior. Workflow selection is not inferred from domain keywords. Changing effort never grants delegation authority.

Supervised context includes a bounded inventory of the project's latest ready file versions so the planner can select relevant exact versions even when the user has not attached them. Inventory metadata is discovery-only; specialists resolve assigned versions into bounded excerpts before they can support citations. The supervisor creates bounded assignments and performs an integration review. When enabled in the model preset, a separate independent-review phase checks the proposed result, rereading assigned immutable sources. Human review remains separate from model execution.

Fresh Report context starts from the goal and eligible evidence, without earlier conversation answers or artifact-comment excerpts. Chat and Team context remains unchanged. Historical reports and checkpoints are not rewritten and may already contain quotations from now-held-out material; start a fresh Report to use the new boundary.

Projects stores a file-level purpose: `project_evidence` is the safe existing default; `reference_report` and `comparison_only` are held out of agent inventory, source reads, visual tools and reports, including explicit attachments. Human previews, originals and immutable versions remain available. `PATCH /api/projects/:projectId/files/:fileId/purpose` requires `projects:read` and `projects:write`, tenant/project-scoped access, and `{ purpose, expectedPurpose }`. A stale `expectedPurpose` returns `409 purpose_conflict`; the compare-and-set update and `projects.file.purpose.updated` audit event commit together. Purpose is selected by a human in the source reader, not automatically classified. No company promotion exists: future company knowledge requires explicit curation, not moving project records. Optional Affinity PDF links do not bypass purpose checks and are not required for example reports.

The enabled V1 retains the required generic `source_reviewer` and `requirements_reviewer` model configurations. A provider/effort preset can additionally configure `sound_insulation`, `construction_law` and `cost_optimizer`; omitted configurations leave those roles disabled. The planner receives only configured available roles, and the server rejects an assignment without a configured specialist model. All roles share the existing budget of at most four tasks per plan; enabling specialists does not increase it.

Assignments are bounded by exact versions in the project inventory or explicitly attached to the run, and return structured summaries, rationale and citations. A specialist receives readable excerpts identified by their exact immutable version IDs. When visual inspection is available, unreadable-text versions also receive inspection IDs, but become citation targets only after a successful visual read. File IDs and uninspected unreadable versions remain invalid citations. Unreadable files remain named coverage gaps, and truncated excerpts must be reported as limited evidence. The server rejects citations without supplied evidence. The optional `independent_reviewer` role receives a fresh review request and re-resolved source excerpts; it can request bounded revisions but cannot approve the result. Uploaded files remain unreviewed evidence until a person reviews them; that status does not prevent an agent from reading them. Domain specialists review and propose: sound insulation prepares acoustic inputs and can use the bounded arithmetic tools below, construction law identifies source-based requirements and applicability uncertainties without legal or compliance approval, and cost options compares evidence-backed alternatives without inventing prices or claiming validated savings. Standards-based engineering verification remains unavailable.

New specialist assignments on recognized models use the same conservative context-capacity accounting as report sections. The source budget reserves the configured output tokens, instructions/schema, variable context and the maximum saved summary/rationale, then packs page-aware, JSON-serialized source slices without a three-slice ceiling. The provider adapter checks the complete assembled prompt before inference. This is conservative byte accounting, not an exact token measurement; neither output settings nor model selection change. New unknown-model assignments use a conservative 48 KiB serialized-evidence allowance without a file-count ceiling. Historical assignments retain their saved layout, including the original three-slice/48 KiB raw-text batches when no context budget was recorded.

Within one assignment, batches remain sequential: each receives the previous concise findings and produces an updated summary within the existing character limits. Oversized pages are split without dropping text or breaking multi-byte characters. Citations may reference only the current batch or validated prior findings, never a future unread batch. Earlier citation references remain retained. Original extraction gaps stay explicit even after every extracted slice has been processed.

Independent specialist assignments run up to the saved preset's `maxParallel` limit. A finished assignment immediately frees its slot for the next one instead of waiting for the slowest assignment in a fixed group. On terminal failure, workers stop taking new assignments or batches and let in-flight calls settle before releasing the lease. Cancellation and replacement leases prevent late writes.

Batch findings and progress are checkpointed in the assignment's existing Postgres JSON state, with the chosen byte limit, an input hash and an audit event. A worker restart can reuse completed batches only when the goal and extracted evidence still match; revisions clear this progress. Retry retains the saved layout, including historical small batches, and completed specialist assignments remain intact when another specialist fails. Larger batches reduce repeated calls and accumulated-findings input, but parallelism alone does not reduce token cost. A terminal timeout does not automatically restart the run or change its model preset.

### Deterministic acoustic tools

`@richtfest/acoustics` owns pure, versioned acoustic arithmetic. OS supplies it through the Knowledge app's host contract; Mastra exposes five tools only to a configured `sound_insulation` specialist with at least two model steps. Other roles and report writers cannot execute them. Existing model, token and step limits are not raised automatically.

| Tool | Supported input and result |
| --- | --- |
| `sum_sound_levels` | Energy sum of uncorrelated simultaneous sound-pressure levels at one receiver, with the same frequency weighting and assessment period |
| `equivalent_sound_level` | Duration-weighted Leq from non-overlapping interval Leq values, not arithmetic averaging or Lmax |
| `composite_sound_reduction` | Area-weighted transmission for side-by-side elements in one octave or third-octave band, not layers in series or weighted Rw/STC ratings |
| `exterior_noise_room_requirement` | Scoped DIN 4109-1/-2:2018-01 room target from assessed La, use-specific factor/minimum, complete exterior geometry and a fixed 2 dB prognosis allowance |
| `exterior_noise_facade` | Simplified weighted-index combination of installed Rw area components and Dn,e,w small elements, with exposure correction and an unrounded room-target margin |

Each observation must carry an exact source-version quotation or an explicit assumption. Source quotations must occur in the specialist's current readable batch and belong to the project. This checks provenance scope, not whether the agent interpreted the number or page correctly. Inputs, applicability and assumptions still require specialist review.

Execution saves a receipt in the existing run-step records, including input snapshot, engine version, formula, reference, unrounded result, intermediates, limitations and `not_reviewed` status. Receipts are available through the run's existing step detail API and supplied to synthesis, concept authoring and independent review. At most 20 distinct receipts are active per assignment. Identical calls within the same work checkpoint reuse the receipt; unchanged retries retain it. Changed evidence or revised assignments clear active receipts without deleting historical records. Cancellation and lease checks fence writes.

The exterior tools are separate from generic single-band arithmetic. They require already assessed La, not Leq/Lden or a noise-zone label. The room tool applies the 35 dB hospital or 30 dB residential/classroom/office base minimum before geometry and uncertainty. Façade composition uses actual area for Rw and A0 = 10 m² per small Dn,e,w element, including multiplicity. Lower-exposure surfaces receive La,max − La,i as a calculation correction, not an improved physical rating. Physical opening areas are used only for inventory accounting, with a 0.01 m² tabulation tolerance; this does not prove the inventory is correct.

Unknown/special applicability, incomplete geometry or element inventory, unadjusted laboratory ratings and required/unknown flanking return `unsupported` with a null result and blocking reason, never a positive comparison. La > 80 dB or a base requirement > 50 dB also requires site-specific assessment. A deliberately conservative flanking gate refuses massive elements with Rw ≥ 50 dB when either the base or geometry-adjusted requirement exceeds 40 dB, regardless of a supplied negligible-flanking claim. No flanking-path engine is implemented. Negative numerical margins remain failures even if rounded display values appear equal.

References include DIN 4109-1:2018-01 §7.1 and the Ziegel March 2022 guide, pp. 45–47. The pp. 103–104 rounded-table example is an arithmetic fixture only: inconsistent window geometry prevents treating it as a validated project. The Holzbau 2019 preliminary charts are not implemented as a general calculation method. Source-guide knowledge drafts preserve editions, exact page citations, original hashes and unresolved errata; author names do not approve or activate rules, and Markdown provenance is not a linked Richtfest file version.

These tools implement reproducible arithmetic and **bounded standards-based screening, not a validated DIN 4109 or ISO 12354 engine**. They do not establish legal applicability, propagation, flanking, regulatory design levels or compliance. Reports must distinguish tool results from imported source claims and retain the human-review warning. The separate `validated_calculation` execution path remains unavailable; these tools are used within supervised project conversations, not as a claim of validated engineering execution.

### Reviewed supplier component context

The [Components app](/docs/workflows/components) supplies `componentContext` to direct execution and the default supervisor phases through host contracts. Reads inherit the initiating actor's tenant and permissions, including `components:read`; agent execution does not grant catalog access. Goal-based product/category matching selects only current reviewed revisions, excluding rejected and unreviewed records. Context contains at most five complete records within 24,000 UTF-8 bytes of serialized record content, with explicit truncation when matches are omitted. Matching is a bounded reference lookup, not a suitability calculation or exhaustive supplier search.

Keep component/revision IDs, external source URL/edition/page, units, configuration conditions and warnings intact. Catalog IDs are not project source-version citation UUIDs, and supplier declarations do not prove which components are installed or specified in a project. Supplier content is untrusted data, not instructions. Human catalog review is not engineering validation, artifact approval or procurement authorization. No reviewed match means no reviewed catalog match, not no suitable product. Supplier snapshot PDFs remain external; runtime context performs no web fetch. Quotes, delivery commitments and installation productivity remain unknown, and V1 has no commercial-offer comparison workflow.

### Upload-time source extraction

Upload completion queues extraction atomically with the ready revision. A Projects app worker extracts each immutable revision once and saves page-linked text, OCR provenance and limitations in Postgres. Readers, direct agents, specialists and independent reviewers reuse that saved extraction rather than repeating OCR. Targeted visual inspection below reads the original separately without replacing saved evidence. A new revision gets its own extraction without changing earlier evidence. The migration queues existing ready uploads with stored originals, and the local demo seed queues its synthetic sources idempotently.

Poppler extracts native PDF text with line breaks and column spacing; pages without meaningful native text are rendered for German and English Tesseract OCR. Page headings distinguish native text, unverified OCR, and blank/unreadable pages or extraction failures. Empty page markers alone do not make a source readable. Extraction is deterministic and does not call an AI provider.

Standalone PNG, JPEG, WebP and BMP images also receive German/English OCR. Affinity Publisher (`.afpub`) originals are streamed to find their largest valid embedded PNG preview; OCR reads only that preview, not native Publisher text or the full document. Missing previews remain explicitly unsupported with a PDF-export recommendation. Preview excerpts always carry a partial-coverage warning and never claim a document page count. A text-free diagram may have no OCR result but still be eligible for visual interpretation below.

Explicit full-PDF representations live in Projects' `projects_source_representations` table, keyed by original version ID with a pinned PDF version and confirming actor/time. `PUT /api/projects/:projectId/source-versions/:versionId/pdf-representation` requires project read/write access, `{ pdfVersionId, expectedPdfVersionId, confirmed: true }` (expected ID is `null` for the first link), ready same-project/same-tenant revisions, an `.afpub` original and a PDF target. `DELETE` requires the expected PDF ID. Row locking and expected-ID checks prevent lost updates; every change is audited atomically. No filename matching, backfill, conversion, extraction retry or approval happens as a side effect.

File listings, version listings and exact-source reads expose `pdfRepresentation`; the agent source inventory also includes pinned historical PDFs. Resolving an original leaves its identity and preview-only content unchanged. Agents must explicitly resolve and cite the PDF version for full-document evidence, and report missing exports rather than infer their contents. The picker offers the linked PDF as a separate evidence choice, so source-membership controls remain intact. New native revisions do not inherit links; later PDF uploads do not advance existing links.

Processing is bounded: 32 MiB per PDF (not an upload limit), 256 Ki characters per saved page, five minutes per worker batch and 45 seconds per subprocess. The worker commits each page before continuing and resumes at the next unsaved page after a deadline or interrupted process. Replica leases prevent concurrent claims; stale workers cannot overwrite saved results. An unfinished page may need to be attempted again after a crash, but committed pages are reused. Storage/interruption recovery stops after three attempts without progress. Unsupported, oversized and unreadable outcomes are saved instead of retried on every read. OCR renders up to 5,000 pixels on the longest side, uses sparse-text recognition for drawing labels, and runs at most two pages concurrently per server process. Text-like files retain a bounded 64 KiB excerpt. Original uploads remain unchanged and available for manual inspection.

Image processing accepts at most 32 MiB and 40 megapixels; Publisher originals are streamed without that source-size cap, with previews bounded to 16 MiB and 16 megapixels. ImageMagick uses signature-selected raster decoders, bounded memory and subprocess deadlines, flattens transparency onto white and reads only the first frame of animated images, marking omitted frames. These are processing limits, not upload limits.

Agents prefer saved structured facts when available. Otherwise they receive up to six saved passages, within 16,000 characters per source, ranked using the task's terms. `resolve_project_source` accepts `textQuery` for fact/passage relevance separately from the filename `query`; explicit `pageStart`/`pageEnd` reads saved original document pages instead, within a 256 Ki-character response budget. Relevant passages carry their original page numbers and explicit coverage limitations: retrieval cannot prove that an omitted requirement or contradiction does not exist. Direct tool follow-ups omit identical duplicate evidence. Independent review, when enabled, deliberately retains broader page-order document evidence rather than inheriting a specialist's relevance selection; it still consumes model tokens but never re-extracts the file.

While extraction is queued or running, the source API returns `processing` immediately and the open reader refreshes until it finishes. Agent execution waits without provider calls for the needed saved evidence (up to ten minutes), honoring cancellation; if processing takes longer, retry the run once it finishes. Extracted text remains unreviewed evidence, not an approved interpretation or a replacement for the original. Temporary extraction files are deleted after processing.

OCR is unverified transcription, not visual understanding of a drawing or a validated measurement. Dimensions, acoustic values, legends, table relationships and spatial associations still require comparison with the original page. Mixed orientations, tiny labels and poor scans can remain unreadable; a processed page is not proof that every detail was recognized. Production includes Poppler, ImageMagick and the German/English Tesseract language data in the application container; no external OCR service receives project files.

### Structured source model

Projects owns three additional Postgres tables: `projects_source_models` records one import attempt per immutable file version, `projects_source_entities` stores revision-scoped entities, and `projects_source_facts` stores typed source claims, units, provenance, evidence and per-fact review state. These are **source claims**, not a merged authoritative building model. Contradictory values coexist; an entity in a new revision never inherits an earlier fact's approval. All queries retain tenant, project and exact-version scope. Model publication and completion are atomic, and worker leases fence concurrent execution.

**IFC2X3 and IFC4** go directly to the local `web-ifc` Node/WASM parser in an isolated worker. No LLM sees raw IFC, and parser failures never fall back to AI. The importer saves object definitions with express IDs and GlobalIds, scalar attributes, occurrence and type property sets, declared quantities, type assignment, spatial containment and decomposition references. Explicit units remain distinct from project defaults; ambiguous defaults and unknown logical values stay explicit. Values are not converted, type properties are not silently merged into instances, and no quantities are calculated from meshes. Other property forms retain structured declarations and unresolved references. Geometry, placements, owner history, other relationships and unit-component resolution are outside this import's scope. Parsing is not engineering or exhaustive IFC validation; originals remain the source of truth. IFC processing has a five-minute deadline and still depends on server memory.

**Document interpretation** divides up to 24,000 saved characters from the first 24 pages into at most six non-overlapping 4,000-character batches, without rereading the original. This is a bounded proposal index, not exhaustive interpretation of a long document. The host rechecks the uploader's active membership, project-read and agent-run permissions, uses the active provider's low-effort supervisor model, resolves that uploader's personal credential before the workspace credential, and caps each response at the lesser of the preset limit and 3,000 tokens. Each batch proposes at most five entities and ten facts, with fewer facts requested for smaller output budgets. It does not delegate or retry automatically. Facts must reference declared entities and exact quotes in that batch; invalid evidence rejects the whole import rather than publishing a partial model. Entity keys are namespaced by batch. Per-batch provider, model, preset, usage and response metadata are saved; diagnostics distinguish token truncation, invalid structure/evidence, provider failure and interruption without retaining raw errors. Missing credentials or permissions leave an explicit terminal state while saved text remains usable. Interrupted attempts become failed rather than risking repeated paid calls. Reads and later credential changes do not requeue them; a new upload revision gets a new attempt. The additive migration queues existing ready stored revisions once, subject to these same permission and configuration checks. Batching can increase total provider cost; configured per-call limits stay unchanged.

**Visual interpretation** includes an image in the first indexing batch only, even when OCR finds no text. The upload-time model worker rereads supported images and Publisher previews once to prepare a metadata-stripped JPEG, at most 1,568 pixels on its longest side and 4 MiB. It supplies native image content to the configured provider alongside any saved OCR, rather than putting base64 in the text prompt. This uses provider image tokens and requires a vision-capable configured model; it does not switch providers or silently retry a rejected image request. No raw image or base64 is stored in model facts or telemetry. Ordinary agent reads reuse persisted facts without another image read or provider call.

Visual facts must use `inferred` provenance and image evidence with the exact supplied scope (`image` or `affinity_preview`) and a supporting description; they cannot invent text quotes or original page numbers. New facts remain unreviewed. Appearance alone does not establish materials, dimensions, acoustic performance or compliance. Publisher preview-only limitations survive both text retrieval and model-fact retrieval; export a PDF to access the full document. Agents wait for the initial visual pass instead of treating absent OCR as absent content, and receive the bounded visual fact index without requiring a keyword match to their task.

Previously saved failed or unsupported outcomes are not automatically reprocessed by deploying new support. An authorized operator can submit an empty body to `POST /api/projects/:projectId/source-versions/:versionId/reprocess`, requiring `projects:read`, `projects:write` and `agent:run`. Recovery queues the model and reuses completed extraction; failed extraction is reset and queued too. Active jobs, completed models and versions with existing facts are rejected. Queueing and its audit record are atomic; the audit retains prior model diagnostics. Originals, version IDs, citations, completed reports and reviews remain unchanged. Re-uploading is unnecessary for recovery. No UI or agent tool queues this operation automatically.

The model API is `GET /api/projects/:projectId/source-versions/:versionId/model`, with `query`, `entityKey`, `offset` and `limit` (up to 100). Text search uses an indexed, punctuation-normalized fact predicate/value vector, so dotted IFC property names remain searchable. Agent reads supply up to 30 selected facts within 16,000 characters, retain review and evidence fields, and expose `model.nextOffset`; `resolve_project_source` accepts `entityKey` and `modelOffset`. Omitted and oversized facts stay explicit; page ranges still retrieve saved document text. IFC evidence uses express IDs instead of invented PDF pages.

Fact review is available through `POST /api/projects/:projectId/source-versions/:versionId/facts/:factId/review`, requiring project-read and existing `knowledge:approve` access, an `expectedRevision`, `status` (`approved`, `rejected` or `unreviewed`) and a note. Concurrent reviews conflict rather than overwrite. The audit trail retains the previous status and reviewer; facts and evidence are immutable. This endpoint is not exposed as an agent tool. There is no dedicated model editor yet. Fact review does not approve an artifact, other claims, an engineering calculation or regulatory compliance.

### Targeted visual inspection

Supervisor execution can use `inspect_project_source` outside planning when the selected role has at least two model steps. It reads an exact in-scope version and one original PDF page, or page 1 of a supported image/Publisher preview, optionally cropped using normalized top-left coordinates. The Projects renderer works independently of saved OCR/index status; the OS host rechecks project-read and agent-run access, tenant, project and ready version. It is not a full-document OCR pass. PDF input is limited to 32 MiB; raster decoding, time and output size remain bounded. A missing preview, unavailable renderer or illegible source remains an explicit limitation.

Each specialist or independent-review call has four distinct visual reads, with duplicate requests cached within that call. Images reach the same model's next step as native media, not base64 text or a separate interpreter's summary. Tool-capable calls reserve their existing final model step for a tool-free structured answer; neither the step allowance nor the output limit is increased. Report outlines, sections, consolidation and preservation checks consume supplied evidence without new visual reads. Durable tool receipts retain exact version, page, crop, scope and image hash, never image bytes. Only successful reads authorize specialist citations for otherwise unreadable sources; receipts restore that authorization on retry. Source membership and call scope still apply. Visual observations are unreviewed inferences, not verified dimensions, calculations or approval. Targeted reads do not establish complete document coverage: acoustic section authoring still requires readable saved evidence for selected ranges, and independent review retains missing-source coverage warnings. Use PDF exports for full Publisher page access.

Requests beyond the four-read allowance receive a durable `budget_exhausted` receipt, not a render failure or an unreadability claim. Once normal specialist batches finish, the application selects up to four exact deferred version/page/crop targets per affected assignment for a visual-only continuation. Each continuation round consumes one **shared** preset revision, rather than adding a separate retry budget. The frozen targets and completed findings survive worker restart; successful sibling work, source batches, calculation receipts and company references are preserved. Actual render failures are not automatically retried. A never-requested source is not classified as unreadable or automatically queued for visual inspection.

When the revision allowance is exhausted—or a model omits the scheduled reads—the remaining targets stay in the assignment receipts and final review metadata. The application prevents an `accept` verdict from hiding those gaps and includes an explicit uninspected-evidence notice in the review-ready result. This remains a draft requiring human review or a focused follow-up, not proof of full visual coverage. Follow-ups do not re-read the full source assignment or enable unrelated tools. Model-step and per-call deadline limits remain separate and unchanged.

## Delegation shape

The supervisor owns coordination and revision. It delegates focused analysis of saved source evidence and requirements structuring, not extraction, then reviews the returned evidence. Presets may enable an additional independent-review provider call; the default remains off to preserve existing behavior and avoid adding cost without workspace choice. That review receives the original goal, specialist results, the supervisor's proposed result, and saved source excerpts. The calculation branch shown in the diagram is a future domain capability and is unavailable in V1. Any eventual deterministic calculation tool remains versioned and requires explicit review before consequential use.

Independent review uses the saved supervisor model, not a separate model choice. Each request contains one copy of its report content, without duplicating template prose or specialist findings. If the report and evidence fit the model's conservative input budget, one call checks them together. Larger inputs are packed by the complete serialized request size, not upload chunks, page count or a three-file ceiling. Evidence passes receive source-linked report sections plus uncited sections; evidence without a report citation receives the full report to check for omissions. A final whole-report consistency pass checks the accumulated findings and cross-section contradictions, without resending raw evidence or erasing earlier blocking findings. Saved templates and source evidence remain unchanged. Unknown models retain a conservative 48 KiB evidence allowance in addition to report context. Upload, extraction and pagination chunks do not themselves schedule review calls.

Mastra workflow checkpoints and workflow run IDs use the Mastra Postgres store. Richtfest domain Postgres records hold conversations, assignments, tasks, evidence links, approvals, events and the policy snapshot. Lease state, replica coordination through Postgres advisory locks, row locks and generation fences make cancellation, restart and resume durable; restart and generation-fencing behavior is covered by the runtime tests. Project source files and revisions remain in private Railway Buckets, while Postgres stores their metadata and references.

The enabled supervisor worker polls queued runs every 1.5 seconds and advances them through the persisted Mastra workflow runtime. Each active supervisor has an independent execution task; each worker process admits up to three runs at a time. Polling fills free slots without waiting for other runs to finish, including runs submitted later in different conversations. This is not a separate server process per thread or an unlimited-concurrency guarantee: additional runs remain queued when all slots are occupied. Locally active runs are excluded from candidate selection even between phases or after a phase lease expires. Shutdown stops new admissions and drains active executions before closing checkpoint storage.

Each run uses a Postgres advisory lock while its checkpoint is read or written, so multiple service replicas can share the queue without advancing the same generation concurrently. Mastra storage keeps workflow checkpoints and run IDs; the Richtfest records remain the source of truth for phase state, assignments, evidence and review outcomes. A queued run therefore remains queued until a worker claims it, then moves through the same durable runtime used for restart and resume.

## Review and control

The supervisor may propose a plan and ask specialists to work, but it does not silently approve consequential outcomes. Project participants can steer a queued or running run, revising its direction; steering cancels its current specialist assignments and starts a new planning generation. A substantive human follow-up after a run has finished starts a new run; agent-to-agent delivery does not. Participants can also cancel active work. Results should remain attributable to the assignment and source evidence that produced them. Unconfigured providers, tools or external actions stay explicit in the UI.

### Messages between agents

Agents can send questions and findings to other runs in the same project, including coordinator–specialist and specialist–specialist exchanges. Direct runs use `send_thread_message({ recipientRunId, body, replyToMessageId? })`; supervisor phases can return up to three entries in their optional `messages` output. The runtime supplies bounded recipient discovery and incoming messages in `context.messaging`. Sender identity comes from the executing run, never model-supplied attribution.

For a new message, `replyToMessageId` may be omitted or set to JSON `null`. The input schema explicitly permits null because strict provider schemas require every property, even optional ones. Null is normalized to omission before validation of delivery scope and retry identity, so switching between the two representations does not duplicate a message. Replies must copy an incoming message's exact ID and target its sender; malformed IDs and references to messages outside those participants remain errors, not silently converted to new messages.

Each exchange appears in both project conversations and in the participating agents' thread views. When both agents share a conversation, it appears only once. Sender and recipient names link to their respective threads; replies link back to the original message. People continue to steer work through the main conversation, rather than a separate specialist composer.

**Delivered does not mean read or executed.** Incoming messages become available to the recipient's next model step. They do not interrupt an in-flight call, cancel assignments, wake a finished run or create automatic reply loops. Late messages still appear live in chat through a conversation-level event stream, independently of run status. If no further step is scheduled, delivery alone does not schedule one. Agent messages are unreviewed collaboration, not source evidence, user instructions or approval.

Delivery requires `agent:run`, `knowledge:write` and project access. Cross-tenant, cross-project, self-addressed and archived-conversation deliveries are rejected. A sender can deliver at most twelve messages across its run and retries, each at most 4,000 characters. The model context includes up to thirty recipients and twelve recent incoming messages, with explicit truncation indicators, within a 16 KiB budget; full messages remain in chat. Document outline and section-authoring calls do not receive the messaging context or send messages.

Conversation copies, immutable delivery receipts and audit events commit atomically under the execution's cancellation/generation fence. Retrying the same operation reuses its receipt instead of publishing duplicates. The nullable `knowledge_messages.agent_message` metadata preserves linked attribution without changing historical messages. Existing source-citation checks and human-review requirements remain in force.

### Reviewed outputs

Each completed supervisor review saves a draft artifact and immutable revision alongside a short conversational handoff. Generic reports use the existing synthesis call to author a separate `document` with a title (up to 300 characters) and Markdown content. Acoustic concepts use the bounded authoring workflow below, which makes additional provider calls. The preset's response limits govern each model response's document content, summary and rationale independently of the output-token budget, not the combined length of a section-authored acoustic concept. Defaults remain 60,000 document characters per response, 10,000 summary characters and 2,000 rationale characters. The optional independent review checks the full document and preserves it alongside its findings. Older saved results without a document continue to use their summary. Manual artifact revision editing accepts up to 500,000 characters, including review notes.

When the plan contains a `sound_insulation` assignment, synthesis must supply a versioned acoustic document template in German or English. The default remains `sound-insulation-review` v1: scope; sources and revisions; requirements and assumptions; room and component references; findings and conflicts; measures and alternatives; open issues and next steps; review status. An explicit Innenlärm or Außenlärm concept/report request fixes the corresponding template server-side; otherwise the saved plan can select a concept. Explicit human steering takes precedence over the original request and model proposal. Generic, ambiguous and combined acoustic reviews retain the review format. Draft, non-calculation and non-compliance warnings are server-authored. The artifact revision retains both the structured template and rendered Markdown. Preview and PDF consume that same saved content, and optional independent review sees the rendered document. Legacy documents without a template keep their existing behavior.

### Reference-derived concept formats

After section assembly, a whole-document editorial pass consolidates prose and removes repetition. A separate semantic preservation gate compares the candidate with the assembled report before optional independent source review and artifact publication. The original `calculationAppendix`, project metadata and original PDF attachments remain immutable; editing cannot introduce calculations or compliance claims. Both the edited candidate and preservation-check result are durably checkpointed in the supervisor record. A checker timeout resumes the saved candidate without editing again. After a rejected check, explicit **Retry run** re-edits using the saved feedback. Incomplete or oversized output, or a failing preservation check, publishes no artifact. Routing sends the goal, selected-source count and bounded conversation message text to TypeSafe—not source files, extracted document bodies, project inventory or credentials. Conversation text can itself contain sensitive information; Shadow is not a data-local mode. The application calls TypeSafe directly at `https://api.typesafe.ai/v1/systemone`, pinned to `jev-1.13.0`, with one attempt and a 1.5-second provider deadline, no automatic retry or provider switching. See the official [API](https://docs.typesafe.ai/api) and [model pricing](https://docs.typesafe.ai/models).

Two independent typed questions classify the workflow and whether it is self-contained. Both reported confidence and the relevant option probabilities must reach the configured threshold (0.9–1; default 0.99). **The default is not calibrated and is not a quality guarantee.** Validate on reviewed German/English examples before choosing Enabled. The model can still misclassify; it never grants permissions or approval.

The fast path requires 1–10 explicitly selected, accessible source versions and a readable-source preflight. Missing/unreadable sources, source-resolution errors, uncertainty, malformed responses, timeout or an unconfigured provider retain normal planning. Custom saved agent profiles, human steering, existing conversation artifacts, annotation context and explicit acoustic-concept/calculation workflows are excluded. Requests over 2,000 characters, histories exceeding 20 messages or containing messages over 1,000 characters, and routing state over 16,000 UTF-8 bytes also retain the planner instead of silently truncating its decision context.

The predefined assignment retains the original goal and exact selected versions. It uses the preset's source reviewer and reads complete saved PDF pages through the existing bounded batching workflow. Source gaps remain explicit. Integration review, configured independent review, revision budgets, cancellation and human approval are unchanged. The optimization does not calculate, certify compliance, approve a result or change the user's generative provider/model/effort. Extra evidence coverage can increase specialist costs, so a skipped planning call does not guarantee a cheaper complete task.

Decision recommendations, probabilities, threshold, routing-contract version `selected-source-summary-jev-v1`, fallback reason and selected route are checkpointed in supervisor history and `decision_routed` events. A worker restart reuses a matching saved decision; changed input, generation or policy invalidates it. Unsaved interrupted calls can still be repeated. Run activity identifies whether the summary workflow or normal planner was selected. Decision attempts and reported usage appear in existing run details and project Analytics, under TypeSafe rather than the selected generative provider. Pricing is an estimate using $0.042 per million input tokens, with output tokens free; absent usage stays unknown. No request or document text is duplicated into decision telemetry.

**Evaluation and cost reporting:**

```sh
# Validate the provisional bilingual cases without any provider request.
bun scripts/evaluate-decision-routing.ts

# After approving provider use, use an already-configured TYPESAFE_API_KEY,
# or an untracked, owner-only plain key file. Never pass a secret CLI argument.
bun scripts/evaluate-decision-routing.ts --live --credential-file /secure/typesafe.key > /secure/routing-results.json

# Score saved responses offline at a candidate threshold.
bun scripts/evaluate-decision-routing.ts --responses /secure/routing-results.json --threshold 0.99

# Operator-only, read-only report; DATABASE_URL must already be configured.
bun scripts/agent-routing-report.ts --tenant TENANT_UUID --project PROJECT_UUID --since 2026-10-12T00:00:00Z
```

The supplied 12 cases are **provisional synthetic examples**, not a reviewed production benchmark. Use `--cases` with domain-reviewed examples, tune only on the calibration split, then evaluate an untouched holdout. The evaluator reports unsafe automatic routes, missed summary routes, failures, latency and known cost separately per split. It checks semantic routing only; deterministic eligibility and complete-task quality require separate evaluation. No quality or savings claim follows from fixture tests.

The scoped report groups recorded run/child costs, outcomes, latency and human ratings by mode, reranking setting, route, provider, model and effort, and breaks attempts down by phase. Missing or unpriced paid attempts prevent full cost averages; reused checkpoints are not new paid calls. Partial recorded totals remain labeled. These observational cohorts are not a causal savings estimate and exclude title generation, source processing and hosting. Compare equivalent requests and review output quality. Switch the preset to Off to stop routing for **new runs**; existing runs keep their snapshots. To stop an active run immediately, cancel it. Removing a credential does not abort an already-sent request, and a lower-priority configured credential can still be resolved.

### Optional company-knowledge reranking

The separate shared-policy flag `knowledgeRerankingEnabled` defaults to **false**. It is independent of `decisionRouting.mode` and belongs to the same immutable saved preset snapshot: changing it affects new runs, not existing runs or their retries.

When enabled, direct agents (including Chat) and supervised specialists' `search_company_knowledge` calls classify relevance with direct TypeSafe `jev-1.13.0`. Retrieval first enforces approved, company-wide, same-tenant candidates. At most 12 candidates, each with at most 2,000 excerpt characters, are sent with their titles, search terms and the requesting run or assignment goal for relevance classification; at most four results are returned. Searches with four or fewer candidates or goals exceeding 2,000 characters skip inference. This transfers company excerpts to TypeSafe and adds paid inference. It is not an approval, factual verification or a promise of lower total task cost. Obtain data-handling approval and evaluate retrieval quality before enabling it.

Jev relevance classifications determine ordering, preserving baseline candidate order for ties. Uncertain classifications, missing credentials, malformed output, timeout or provider errors fall back to the baseline search order. Classifier attempts and available usage are tracked in existing attempt/usage telemetry; missing usage remains unknown. The original search budgets, approval/content rechecks, saved receipts and human review remain in force. Credentials resolve personal → workspace → server environment, just as for routing. Standalone company-library search remains unchanged. Generative provider selection, existing reviews, approvals and engineering-calculation boundaries are unchanged.

Both reported confidence and the chosen probability must reach 0.9 for every candidate; otherwise the complete baseline order is retained. This is an uncalibrated guard, not a correctness guarantee. The contract is `approved-company-relevance-jev-v1`. Reranking runs outside the shared checkpoint lock, and the receipt commit rechecks authorization, current evidence and cancellation. Concurrent duplicate searches can incur separate in-flight classifier costs, although only one receipt is retained.

Use `bun scripts/evaluate-knowledge-reranking.ts` for a no-network description, or add `--live` with `TYPESAFE_API_KEY` and a migrated **disposable local** `DATABASE_URL` to compare SQL-only and Jev retrieval. The script inserts and removes isolated synthetic records, reports top-four recall, latency and inference cost, and never reads customer knowledge. Its four bilingual cases deliberately place keyword-heavy distractors ahead of the useful reference; they are a challenge set, not representative quality evidence or a downstream cost benchmark. Both paths still return four excerpts.

### Model and response limits

Models are edited in one inline role table. Optional specialists stay in place with disabled, empty fields until enabled; enabling copies the corresponding reviewer's current settings into that row for further editing. Disabling removes that specialist from the saved preset. Independent review stays beside the effort selector, and shared execution limits are grouped below the table. Save applies the selected preset; reset restores its vendor defaults. On narrow screens, the table scrolls horizontally without widening the page. **Manage connection** opens AI connections for credentials and active-provider selection; it does not change the provider from the model editor.

In **Settings → Agent model settings**, select the effort preset and edit **Response limits**:

| Setting | Default | Allowed range |
| --- | --- | --- |
| Summary characters | 10,000 | 1,000–100,000 |
| Rationale characters | 2,000 | 500–20,000 |
| Document characters per response | 60,000 | 1,000–200,000 |
| Call timeout (seconds) | 180 | 10–600 |

These whole-number limits apply to the supervisor and all specialists in that preset, including independent review and direct execution. Character limits are ceilings, not requested response lengths; token budgets still apply separately. Document characters bounds single-response documents (including their rendered template content), not section-authored acoustic reports; acoustic authoring pieces instead use a soft 12,000-character writing target. Summary and rationale limits remain hard ceilings. The timeout bounds each model call, not the entire run, and applies to every automatic retry. A timeout is reported explicitly with guidance to increase this setting or request a shorter answer, rather than being labeled as a generic connection failure. Higher limits can increase runtime and cost; provider-specific limits still apply.

Save the preset and **start a new request** to use changed limits. Saving never starts inference. Existing runs and ordinary retries keep their original snapshot; timeouts are not automatically retried. Legacy presets receive the defaults above for new runs. Historical supervisor snapshots retain their original character caps and phase-specific deadlines; historical direct runs retain their original 50,000-character draft cap and 60-second timeout. Reset restores the provider's vendor defaults. Changes use the existing audited, administrator-only preset workflow and do not require a database migration.

For OpenAI and Anthropic, the model fields in Settings use the connected provider credential to load the account's available model catalog. Credentials remain server-side; Settings shows a masked placeholder for a saved key and never returns its secret value. GPT 6 models and Claude Opus 5.5 / Sonnet 5.5 models are grouped first; other models returned by the provider remain selectable. Existing model IDs are retained in the selector if they are no longer returned by the catalog. Vercel AI Gateway model IDs remain manually configured because its public catalog does not indicate which models an account can use.

The workspace provider setting selects the active provider for direct and supervisor execution. Empty model IDs leave Anthropic and Vercel presets unconfigured; OpenAI retains its `gpt-4.1-mini` direct default when no model environment value is supplied. The UI does not invent or silently switch providers. Vercel presets use `provider/model` Gateway IDs at `https://ai-gateway.vercel.sh/v1` and do not fall back to OpenAI or Anthropic on a gateway failure. Vendor defaults can be restored by an administrator through Settings.

## Agent profiles

Settings → Agents separately configures workspace profiles for Supervisor (`supervisor`), Source reviewer (`source_reviewer`), Requirements reviewer (`requirements_reviewer`), Independent reviewer (`independent_reviewer`), Sound insulation specialist (`sound_insulation`), Construction law specialist (`construction_law`) and Cost options specialist (`cost_optimizer`). Users with both `knowledge:read` and `access:manage` can save plain-language role instructions, routing phrases and assigned knowledge. These controls customize the supported team; they do not enable an omitted model configuration, create new roles or grant permissions. Agent model settings control whether the independent-review pass runs for a preset; legacy and vendor presets default to off.

Use instructions for working preferences within a role, such as checking dimensions before summarizing a source. These are optional additions to the built-in runtime instructions: an empty field retains built-in behavior and does not mean the agent is unconfigured. Routing phrases are optional hints the supervisor considers while planning assignments, not guaranteed triggers. Assign only approved company-wide knowledge: project-specific or unapproved drafts cannot be selected. Company references guide the work but do not replace the project's source evidence or supply project-version citations.

Each new durable supervisor run saves the profile versions, instructions, routing phrases and assigned reference content in its own snapshot. Planning, specialist work and review use that snapshot, so later settings or knowledge edits do not rewrite the run's context. Existing runs without a profile snapshot retain the original defaults.

Project agents can also call **`search_company_knowledge`** without a profile assignment. Direct runs allow up to two searches within their existing tool round. All configured supervised specialist roles receive the tool when their snapshotted model allows at least two steps. Planning remains tool-free; reviewers receive the specialists' saved references instead of another retrieval tool. The built-in instructions ask agents to search relevant company guidance before declaring it absent. Tool availability does not guarantee that a model will choose to search or rely on a result.

The calling agent supplies one to eight short subject terms and may pass a `category` UUID to restrict retrieval. Direct agents and search-enabled specialists receive `context.companyKnowledgeCategories`: up to 100 tenant-private category IDs and names within 8 KiB, with an explicit `truncated` flag. This directory requires knowledge-read access, consumes no tool round and does not claim that a category contains approved entries. Names are reference data, not instructions. Use `_none` for unfiled entries; omission, JSON `null` and `all` all mean unrestricted category search. A category name is not a valid filter ID, and subject terms still match entry text rather than category names. Unknown or other-tenant category IDs return no matches, never a broader search.

Search terms contain Unicode letters/numbers, whitespace and hyphens, with 1–80 characters after trimming. The application enforces that character rule locally. The provider-facing tool schema describes it without exporting JavaScript Unicode-property regex syntax, which OpenAI rejects. Input limits and retrieval access checks remain enforced before search.

Baseline retrieval reuses the company library's PostgreSQL full-text matching and exact source windows, without embeddings or nested AI calls. Only the explicitly enabled reranking option above adds a classifier call, restricted to the same category filter. Tenant, company scope and **approved** status are enforced by the application, not selected by the model. Each search returns at most four entries and 2,000 excerpt characters per entry. Results including labels fit within 48,000 serialized bytes; unusually large escaped content can return fewer entries, retaining the highest-ranked exact excerpts. A specialist assignment retains at most two distinct terms/category searches across batches and retries; further distinct requests return `limit_reached`, not a model failure. Repeated searches recheck the saved references and return `already_retrieved` with their receipt ID, without duplicating excerpts already supplied in context or tool results. Unrestricted searches retain their historical retry identity, including when strict providers send null. Empty results and omitted text remain explicit coverage limits. Existing token, step, parallelism and source-batching allowances are unchanged; the category directory and result labels fit within the existing reserved tool context.

Sibling specialists' full-text reads run outside the shared supervisor checkpoint lock, allowing searches to overlap. Receipt commits remain serialized: they recheck cancellation and the execution lease, enforce each assignment's search budget, deduplicate concurrent identical requests and verify current approval and content before saving results. A cancelled or replaced execution cannot publish an in-flight search result.

Audited run-step receipts retain terms, the optional category filter, entry IDs, original titles, exact excerpts and SHA-256 body hashes. New results also include category ID/name, display title, source label and chapter when available (names bounded to 100 characters, other labels to 300). Historical receipts without these labels remain readable. Specialist assignments and batch history retain those receipts alongside their findings, and pass them into synthesis, acoustic report sections and independent review. References participate in report checkpoint fingerprints. Reports attribute guidance by entry title; company-entry and receipt UUIDs never become project-file citations or calculation-input provenance. A receipt proves retrieval, not that a reference supports a particular conclusion or was actually used. Inspect the receipt together with the findings to assess reliance and applicability.

Search reads are rechecked on retry. Before continuing work from retrieved snapshots, the runtime verifies that entries still belong to the tenant, remain approved company knowledge and retain the same title and body hash. Changed or withdrawn references stop that continuation and require a new run; historical receipts stay intact for inspection. Organization labels describe the retrieval-time folder/source/chapter: later moves or label edits alone do not revoke approved content or invalidate specialist receipts. This rule concerns searched references and does not rewrite the separate profile snapshots described above. No schema migration, automatic approval or production inference is part of enabling this tool.

Workspace instructions remain subordinate to the platform safety and output contract. They cannot expand source access, change supported roles, bypass human review, approve an output, authorize external actions or relax structured output and citation validation. Engineering calculations remain unavailable until a validated deterministic tool exists.

### Planned template uploads in agent settings

Template upload and management are **not implemented yet**. The intended home is **Settings → Agents**, alongside the role's existing guidance, not a new app or separate access permission. The next workflow should let authorized administrators upload a reference PDF, inspect its extracted structure, review the reusable template and assign an immutable version to a role. Reference documents must be labeled as output examples rather than project evidence or executable instructions.

Originals and immutable file revisions should use private Railway Buckets with tenant-scoped metadata, review status and assignments in Postgres. The Knowledge app owns the template workflow and receives storage/access capabilities through its host contract. A new run should snapshot the reviewed template version along with its existing profile guidance; later uploads must not rewrite running work or historical artifact revisions. The current structured template ID/version and revision payload provide the output-side contract, but there is no upload API, template library or settings selector in this first pass. Uploading a project source today does not register it as a workspace output template.

## Runtime setup

The supervisor worker is disabled by default in local development and enabled in production with `AGENT_SUPERVISOR_ENABLED=true`. Before enabling it in a new environment, apply the standard application migrations and configure model presets. The application migration provisions the Mastra workflow checkpoint schema in `rf_agent_runtime` and copies compatible snapshots from the former runtime schema when present. The planner routes file-based work to source and requirements reviewers. Project files are readable as unreviewed evidence; human review applies to the proposed result. If a user explicitly asks to review every project source, assignments cover the available inventory or report the coverage limit.

For a new environment, apply the standard application migrations first, configure model presets, and only then enable the worker:

```sh
bun run --filter '@richtfest/api' db:migrate
AGENT_SUPERVISOR_ENABLED=true bun run --filter '@richtfest/api' dev
```

The application starts the worker with automatic Mastra store initialization disabled, so `db:migrate` must complete before queued runs can be claimed. The `db:migrate-agent-runtime` script remains available for explicit full-store setup, but it is not required for the supervisor workflow checkpoint tables. When enabled, the worker logs its startup, polling failures and per-run execution failures with the run ID and generation; repeated errors are rate-limited to keep the API log useful.

The enablement flag only turns on the worker. A workspace administrator must configure a valid model ID and bounded preset values for the selected provider and effort in Settings before starting a run. Vendor model environment variables may provide defaults, but Richtfest does not automatically choose a frontier model, infer a paid model or treat a provider API key as a complete preset. Anthropic presets omit reasoning effort because that adapter does not accept the field.

The runtime policy snapshot answers which supervisor and specialist models, limits, independent-review setting and preset version governed a run. Domain records answer what the specialists found, which source revisions support it, what the independent reviewer flagged and whether a person approved it. These are separate records: a valid runtime snapshot does not make a calculation tool available, approve a result or certify engineering or regulatory compliance.

The runtime verification uses synthetic Mastra/provider fixtures and Postgres restart and fencing tests. The domain-specialist and template extension prepares contracts and checks mock-provider execution; it does not validate engineering results or real-provider quality. Migration `0028_domain_agent_profiles` expands the profile-key constraint to all seven supported roles without rewriting existing guidance or snapshots. Apply it before saving domain profiles; source-import migrations remain separate.

1. Project chat sends a prompt and project context to OS authentication and access checks.
2. The Mastra supervisor receives the authorized context and routes durable assignments to the generic reviewers and any domain specialists configured in the selected provider/effort preset.
3. Those specialists perform bounded review/proposal work within the existing four-task ceiling and return structured results with evidence.
4. The supervisor integrates and reviews the result set. If the preset enables independent review, a fresh reviewer pass re-reads assigned sources and can request bounded revisions. A human may steer, approve or cancel. Calculation work is unavailable in V1 and remains a future capability.
