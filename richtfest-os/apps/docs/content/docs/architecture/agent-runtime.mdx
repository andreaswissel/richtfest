## Gated V1

Project chat is the entry point for agentic work. The Richtfest OS host authenticates the actor, applies workspace and role access, and passes the approved context to a Mastra supervisor. Context includes a bounded inventory of the project's latest ready file versions so the planner can select relevant exact versions even when the user has not attached them. Inventory metadata is discovery-only; specialists resolve assigned versions into bounded excerpts before they can support citations. The supervisor interprets the request, creates bounded assignments and performs an integration review. When enabled in the model preset, a separate independent-review phase re-resolves the assigned immutable sources and checks the proposed result before the draft is saved. A human can steer, approve or cancel the run at the review boundary.

The enabled V1 retains the required generic `source_reviewer` and `requirements_reviewer` model configurations. A provider/effort preset can additionally configure `sound_insulation`, `construction_law` and `cost_optimizer`; omitted configurations leave those roles disabled. The planner receives only configured available roles, and the server rejects an assignment without a configured specialist model. All roles share the existing budget of at most four tasks per plan; enabling specialists does not increase it.

Assignments are bounded by exact versions in the project inventory or explicitly attached to the run, and return structured summaries, rationale and citations. A specialist receives only readable excerpts, identified by their exact immutable version IDs; file IDs and unreadable source IDs are not citation targets. Unreadable files remain named coverage gaps, and truncated excerpts must be reported as limited evidence. The server still rejects citations outside the assigned readable versions. The optional `independent_reviewer` role receives a fresh review request and re-resolved source excerpts; it can request bounded revisions but cannot approve the result. Uploaded files remain unreviewed evidence until a person reviews them; that status does not prevent an agent from reading them. Domain specialists review and propose only: sound insulation prepares acoustic input proposals, construction law identifies source-based requirements and applicability uncertainties without legal or compliance approval, and cost options compares evidence-backed alternatives without inventing prices or claiming validated savings. No deterministic acoustic engine or other engineering calculation is available in this workflow.

Specialist evidence is processed in sequential batches of at most three source slices and 48 KiB of extracted UTF-8 text. Oversized excerpts are split without dropping text or breaking multi-byte characters, preferring line boundaries. This is a raw-evidence byte budget, not an exact token count or a limit on the whole prompt; instructions, profile guidance and prior findings are additional context. Each batch receives the previous concise findings and produces an updated summary within the existing character limits. Citations may reference only the current batch or validated prior findings, never a future unread batch. Earlier citation references remain retained. Original extraction gaps stay explicit even after every extracted slice has been processed.

Batch findings and progress are checkpointed in the assignment's existing Postgres JSON state, with an input hash and an audit event. A worker restart can reuse completed batches only when the goal and extracted evidence still match; revisions clear this progress. Completed specialist assignments remain intact when another specialist fails. Batching may use more model calls for large assignments, but avoids repeatedly sending all raw files in one request. A terminal timeout does not automatically restart the run or change its model preset.

### Upload-time source extraction

Upload completion queues extraction atomically with the ready revision. A Projects app worker extracts each immutable revision once and saves page-linked text, OCR provenance and limitations in Postgres. Readers, direct agents, specialists and independent reviewers use that saved extraction; opening a source or starting another run never downloads or extracts it again. A new revision gets its own extraction without changing earlier evidence. The migration queues existing ready uploads with stored originals, and the local demo seed queues its synthetic sources idempotently.

Poppler extracts native PDF text with line breaks and column spacing; pages without meaningful native text are rendered for German and English Tesseract OCR. Page headings distinguish native text, unverified OCR, and blank/unreadable pages or extraction failures. Empty page markers alone do not make a source readable. Extraction is deterministic and does not call an AI provider.

Standalone PNG, JPEG, WebP and BMP images also receive German/English OCR. Affinity Publisher (`.afpub`) originals are streamed to find their largest valid embedded PNG preview; OCR reads only that preview, not native Publisher text or the full document. Missing previews remain explicitly unsupported with a PDF-export recommendation. Preview excerpts always carry a partial-coverage warning and never claim a document page count. A text-free diagram may have no OCR result but still be eligible for visual interpretation below.

Processing is bounded: 32 MiB per PDF (not an upload limit), 256 Ki characters per saved page, five minutes per worker batch and 45 seconds per subprocess. The worker commits each page before continuing and resumes at the next unsaved page after a deadline or interrupted process. Replica leases prevent concurrent claims; stale workers cannot overwrite saved results. An unfinished page may need to be attempted again after a crash, but committed pages are reused. Storage/interruption recovery stops after three attempts without progress. Unsupported, oversized and unreadable outcomes are saved instead of retried on every read. OCR renders up to 5,000 pixels on the longest side, uses sparse-text recognition for drawing labels, and runs at most two pages concurrently per server process. Text-like files retain a bounded 64 KiB excerpt. Original uploads remain unchanged and available for manual inspection.

Image processing accepts at most 32 MiB and 40 megapixels; Publisher originals are streamed without that source-size cap, with previews bounded to 16 MiB and 16 megapixels. ImageMagick uses signature-selected raster decoders, bounded memory and subprocess deadlines, flattens transparency onto white and reads only the first frame of animated images, marking omitted frames. These are processing limits, not upload limits.

Agents prefer saved structured facts when available. Otherwise they receive up to six saved passages, within 16,000 characters per source, ranked using the task's terms. `resolve_project_source` accepts `textQuery` for fact/passage relevance separately from the filename `query`; explicit `pageStart`/`pageEnd` reads saved original document pages instead, within a 256 Ki-character response budget. Relevant passages carry their original page numbers and explicit coverage limitations: retrieval cannot prove that an omitted requirement or contradiction does not exist. Direct tool follow-ups omit identical duplicate evidence. Independent review, when enabled, deliberately retains broader page-order document evidence rather than inheriting a specialist's relevance selection; it still consumes model tokens but never re-extracts the file.

While extraction is queued or running, the source API returns `processing` immediately and the open reader refreshes until it finishes. Agent execution waits without provider calls for the needed saved evidence (up to ten minutes), honoring cancellation; if processing takes longer, retry the run once it finishes. Extracted text remains unreviewed evidence, not an approved interpretation or a replacement for the original. Temporary extraction files are deleted after processing.

OCR is unverified transcription, not visual understanding of a drawing or a validated measurement. Dimensions, acoustic values, legends, table relationships and spatial associations still require comparison with the original page. Mixed orientations, tiny labels and poor scans can remain unreadable; a processed page is not proof that every detail was recognized. Production includes Poppler, ImageMagick and the German/English Tesseract language data in the application container; no external OCR service receives project files.

### Structured source model

Projects owns three additional Postgres tables: `projects_source_models` records one import attempt per immutable file version, `projects_source_entities` stores revision-scoped entities, and `projects_source_facts` stores typed source claims, units, provenance, evidence and per-fact review state. These are **source claims**, not a merged authoritative building model. Contradictory values coexist; an entity in a new revision never inherits an earlier fact's approval. All queries retain tenant, project and exact-version scope. Model publication and completion are atomic, and worker leases fence concurrent execution.

**IFC2X3 and IFC4** go directly to the local `web-ifc` Node/WASM parser in an isolated worker. No LLM sees raw IFC, and parser failures never fall back to AI. The importer saves object definitions with express IDs and GlobalIds, scalar attributes, occurrence and type property sets, declared quantities, type assignment, spatial containment and decomposition references. Explicit units remain distinct from project defaults; ambiguous defaults and unknown logical values stay explicit. Values are not converted, type properties are not silently merged into instances, and no quantities are calculated from meshes. Other property forms retain structured declarations and unresolved references. Geometry, placements, owner history, other relationships and unit-component resolution are outside this import's scope. Parsing is not engineering or exhaustive IFC validation; originals remain the source of truth. IFC processing has a five-minute deadline and still depends on server memory.

**Document interpretation** uses at most one provider call over up to 24,000 saved characters from the first 24 pages, not another original-file read. This is a bounded proposal index, not exhaustive interpretation of a long document. The host rechecks the uploader's active membership, project-read and agent-run permissions, uses the active provider's low-effort supervisor model, resolves that uploader's personal credential before the workspace credential, and caps output at the lesser of the preset limit and 3,000 tokens. It does not delegate or retry. Facts must reference declared entities and exact quotes on supplied pages; invalid evidence rejects the proposal. Provider, model, preset version and reported usage—including available usage on failed validation—are saved. Missing credentials or permissions leave an explicit terminal state while saved text remains usable. Interrupted attempts become failed rather than risking a second paid call. Reads and later credential changes do not requeue them; a new upload revision gets a new attempt. The additive migration queues existing ready stored revisions once, subject to these same permission and configuration checks.

**Visual interpretation** extends that same single provider call for supported images and Publisher previews, even when OCR finds no text. The upload-time model worker rereads the original once to prepare a metadata-stripped JPEG, at most 1,568 pixels on its longest side and 4 MiB. It supplies native image content to the configured provider alongside any saved OCR, rather than putting base64 in the text prompt. This uses provider image tokens and requires a vision-capable configured model; it does not switch providers or silently retry a rejected image request. No raw image or base64 is stored in model facts or telemetry. Later agent reads reuse persisted facts without another image read or provider call.

Visual facts must use `inferred` provenance and image evidence with the exact supplied scope (`image` or `affinity_preview`) and a supporting description; they cannot invent text quotes or original page numbers. New facts remain unreviewed. Appearance alone does not establish materials, dimensions, acoustic performance or compliance. Publisher preview-only limitations survive both text retrieval and model-fact retrieval; export a PDF to access the full document. Agents wait for the initial visual pass instead of treating absent OCR as absent content, and receive the bounded visual fact index without requiring a keyword match to their task.

Previously saved unsupported outcomes are not automatically reprocessed by deploying new format support. Upload a new revision or explicitly arrange scoped operator reprocessing of the old extraction and model jobs; completed reports and approvals remain unchanged.

The model API is `GET /api/projects/:projectId/source-versions/:versionId/model`, with `query`, `entityKey`, `offset` and `limit` (up to 100). Text search uses an indexed, punctuation-normalized fact predicate/value vector, so dotted IFC property names remain searchable. Agent reads supply up to 30 selected facts within 16,000 characters, retain review and evidence fields, and expose `model.nextOffset`; `resolve_project_source` accepts `entityKey` and `modelOffset`. Omitted and oversized facts stay explicit; page ranges still retrieve saved document text. IFC evidence uses express IDs instead of invented PDF pages.

Fact review is available through `POST /api/projects/:projectId/source-versions/:versionId/facts/:factId/review`, requiring project-read and existing `knowledge:approve` access, an `expectedRevision`, `status` (`approved`, `rejected` or `unreviewed`) and a note. Concurrent reviews conflict rather than overwrite. The audit trail retains the previous status and reviewer; facts and evidence are immutable. This endpoint is not exposed as an agent tool. There is no dedicated model editor yet. Fact review does not approve an artifact, other claims, an engineering calculation or regulatory compliance.

## Delegation shape

The supervisor owns coordination and revision. It delegates focused analysis of saved source evidence and requirements structuring, not extraction, then reviews the returned evidence. Presets may enable an additional independent-review provider call; the default remains off to preserve existing behavior and avoid adding cost without workspace choice. That review receives the original goal, specialist results, the supervisor's proposed result, and saved source excerpts. The calculation branch shown in the diagram is a future domain capability and is unavailable in V1. Any eventual deterministic calculation tool remains versioned and requires explicit review before consequential use.

Mastra workflow checkpoints and workflow run IDs use the Mastra Postgres store. Richtfest domain Postgres records hold conversations, assignments, tasks, evidence links, approvals, events and the policy snapshot. Lease state, replica coordination through Postgres advisory locks, row locks and generation fences make cancellation, restart and resume durable; restart and generation-fencing behavior is covered by the runtime tests. Project source files and revisions remain in private Railway Buckets, while Postgres stores their metadata and references.

The enabled supervisor worker polls queued runs every 1.5 seconds and advances them through the persisted Mastra workflow runtime. Each active supervisor has an independent execution task; each worker process admits up to three runs at a time. Polling fills free slots without waiting for other runs to finish, including runs submitted later in different conversations. This is not a separate server process per thread or an unlimited-concurrency guarantee: additional runs remain queued when all slots are occupied. Locally active runs are excluded from candidate selection even between phases or after a phase lease expires. Shutdown stops new admissions and drains active executions before closing checkpoint storage.

Each run uses a Postgres advisory lock while its checkpoint is read or written, so multiple service replicas can share the queue without advancing the same generation concurrently. Mastra storage keeps workflow checkpoints and run IDs; the Richtfest records remain the source of truth for phase state, assignments, evidence and review outcomes. A queued run therefore remains queued until a worker claims it, then moves through the same durable runtime used for restart and resume.

## Review and control

The supervisor may propose a plan and ask specialists to work, but it does not silently approve consequential outcomes. Project participants can steer a queued or running run, revising its direction; steering cancels its current specialist assignments and starts a new planning generation. A message sent after a run has finished starts a new run. Participants can also cancel active work. Results should remain attributable to the assignment and source evidence that produced them. Unconfigured providers, tools or external actions stay explicit in the UI.

Each completed supervisor review saves a draft artifact and immutable revision alongside a short conversational handoff. The existing synthesis call authors a separate `document` with a title (up to 300 characters) and Markdown content; this does not add a provider call. The preset's response limits govern document content, summaries and rationale independently of the output-token budget. Defaults remain 60,000 document characters, 10,000 summary characters and 2,000 rationale characters. The optional independent review checks the full document and preserves it alongside its findings. Older saved results without a document continue to use their summary. Generated documents remain editable with headroom for review notes (up to 500,000 characters per saved artifact revision).

When the plan contains a `sound_insulation` assignment, synthesis must supply a versioned acoustic document template in German or English. The default remains `sound-insulation-review` v1: scope; sources and revisions; requirements and assumptions; room and component references; findings and conflicts; measures and alternatives; open issues and next steps; review status. For an explicit Innenlärm or Außenlärm concept/report request, synthesis is instructed to choose the corresponding concept format below. Generic, ambiguous and combined acoustic reviews retain the review format. Draft, non-calculation and non-compliance warnings are server-authored. The artifact revision retains both the structured template and rendered Markdown. Preview and PDF consume that same saved content, and optional independent review sees the rendered document. Legacy documents without a template keep their existing behavior.

### Reference-derived concept formats

The supplied completed **Innenlärmkonzept (4 May 2026)** and **Außenlärmkonzept (29 April 2026)** establish output-structure references, not reusable project evidence. The former has a 34-page concept and a separately numbered 26-page calculation appendix; the latter has a 16-page concept and a 72-page calculation appendix. Their page counts, project details, products, numeric results, signatures and compliance conclusions are not template defaults.

| Versioned format | Main section order |
| --- | --- |
| `interior-noise-concept` v1 | Preliminary remarks; requirements and standards; interior-noise plans; component specifications; verification and planning requirements, including development plan; building services, stairs and sanitary installations; air-to-water heat pump; agreed protection level and DEGA reference |
| `exterior-noise-concept` v1 | Preliminary remarks; exterior-noise assessment; development plan; component specifications; exterior-noise plans |

Both formats include project metadata, a generated contents list, source revisions, open issues, an explicit review/acknowledgment status and a final calculation-evidence inventory. Unknown metadata remains visibly missing. Required sections must describe missing evidence or inapplicability instead of disappearing. Section bodies support paragraphs, lists and tables; top-level structure and warnings come from the versioned renderer. Existing source citation checks also cover these formats. The total rendered document uses the preset's document character limit (60,000 by default), including headings and warnings.

The authoring instructions distinguish statutory minimum from agreed protection, and imported/source-stated values from inferred or approved facts. Tables should retain component/room identity, source/page, build-up, requirement, cited available value, units and review status. Exterior assessment separates source, orientation and day/night levels. Plans are a source-linked drawing register; the appendix inventories existing calculation evidence with method/tool and input revision where supplied. Neither section claims that new drawings or a full calculation appendix have been generated or attached.

This first implementation adapts the reference **structure**, using the existing Richtfest Markdown/PDF presentation. It does not reproduce the original branded cover, landscape plan sheets, graphical overlays, printed contents page numbers, signatures or a separately paginated calculation attachment. The PDF renderer still does not fetch or embed images. No example calculation or normative table is copied, and no engineering calculation capability is enabled. Template selection and content quality still require real-provider evaluation; automated coverage uses synthetic provider/evidence fixtures.

Room/component references are proposals into the existing source model, not new BIM records or approved calculation inputs. Copy the exact source `versionId`, `entityKey` from the importer's `entity.key`, and `globalId` from `entity.globalId`, retaining case. Missing entity keys, GlobalIds and page references are `null`; do not manufacture them. IFC `#expressID` keys are local to the cited revision, not cross-version identity; a GlobalId does not itself establish reviewed equivalence between revisions. Reuse saved IFC facts with their provenance and individual review status rather than re-extracting or claiming verified geometry, properties or completeness. Rejected facts must not support proposed measures. The source import remains the separate Projects capability described above.

The conversation displays a registered OpenUI PDF attachment whose title opens the exact saved revision and whose download action exports it. Workspace and print views render headings, lists and tables. The server PDF uses bundled Unicode fonts, paginated tables and a source register; it does not execute HTML or fetch embedded images. Source labels come from authorized project metadata for the exact cited version, not model-authored names or the latest upload. Missing sources are marked unavailable. PDF generation reads the saved revision and does not approve or publish it; older revisions are labeled historical instead of inheriting the current artifact's approval. Reviewing the supervisor run and approving the artifact are separate actions; completion does not publish reviewed knowledge. A follow-up result creates a new draft, while retrying the same completed generation reuses its saved result.

New runs use the preset's configurable per-call deadline (180 seconds by default). Historical supervisor snapshots without a timeout retain 60 seconds for planning and 180 seconds for specialist, synthesis and independent-review calls. An application deadline stops the call with an explicit timeout reason rather than repeating the same request unchanged. Timeout guidance recommends adjusting the timeout for a new run, a narrower assignment or a faster model, not an output-token increase or credential repair. Cancellation remains separate. The effective deadline is recorded in each attempt's settings.

Other transient provider failures, including rate limits, service errors and invalid structured model responses, are retried with up to three attempts. Provider cooldowns are honored up to five minutes; longer cooldowns stop automatic recovery without sending an early request. Without a provider cooldown, rate limits wait five and ten seconds, while other transient failures use short backoff. Permission and configuration errors are not retried automatically. Live summaries restart cleanly for each attempt. If a run still fails, the conversation shows a terminal outcome in chronological order with the recorded safe reason, run details and a manual retry action. Provider exception text is not persisted because it can contain credentials or request data.

Mastra structured-output errors are recognized by their stable error IDs, including serialized codes, even when no nested validation error is available. Truncated, missing or schema-invalid structured results use the invalid-response retry path rather than being reported as connection failures. Validation retries include the preceding call's allowlisted error IDs, field paths and limits, with explicit correction instructions. For overlong summaries or rationale, the model is asked to rewrite concisely with headroom while retaining important findings, citations and limitations. Feedback stays with the affected call, not parallel specialists, and does not include the rejected text or raw provider errors. Retries keep the selected model, output budget, schema and three-attempt cap unchanged; incomplete results are never accepted or silently truncated. A model can still fail to comply, in which case the run retains a visible terminal failure.

An output-length failure does **not** automatically split an assignment or create more subagents. The retry asks the same agent to rewrite within the field limit, aiming below half that limit, and leaves successful sibling results alone. Source batching is a separate input-processing mechanism, not an output-overflow recovery strategy. If three total attempts fail, a person must narrow or split the request before starting another run.

Chat, activity and run details distinguish confirmed output truncation from a summary exceeding its character limit. Increasing tokens does not fix a character-limit failure. Failed workspace runs include safe terminal-call diagnostics on initial load, including the responsible specialist when available; details do not depend on having opened the run panel first.

For confirmed length truncation with a known role and policy snapshot, chat offers **Yes**, **No**, or **Describe what Richtfest should do differently**. Yes requires workspace administration access and doubles only the affected role's output limit, capped at 128,000. It checks the current preset version, model and limit before saving, records an audit event and leaves all other settings unchanged. Model-specific limits still apply; longer output can cost more and take longer. No dismisses the offer without changing settings. Describe focuses the composer without sending a message. Saving affects new runs only: it does not start a run, alter active/history snapshots or change the existing **Retry run** action, which retains the original snapshot. Start a new request to use the updated preset.

Each failed or retrying provider-call event retains bounded diagnostic metadata: the call ID, attempt number, executing run ID, allowlisted structured-output error ID and finish reason, and known-schema validation fields/codes/limits when recoverable. The call ID corresponds to the durable attempt's operation ID; together with the run and attempt number it links diagnostics to that attempt and its usage. This distinguishes output truncation from schema failure without storing the rejected response, exception messages, credentials, stacks or arbitrary field names. Failed-attempt usage is retained when Mastra exposes it, once per attempt. Missing metadata stays unknown: some wrappers discard validation details, and a schema failure may expose `error` when the upstream finish reason is unavailable. These diagnostics are available in persisted run events and the authorized run-detail API; they do not retroactively recover details from older runs.

The project workspace keeps the main conversation focused on the request and result. Its Subagents panel lists each specialist by a readable name and status; prior cancelled work is collapsed. Open a row to inspect that specialist's dedicated, read-only thread with its assignment, result and source links. These threads use the durable run and activity records, not a second editable conversation. Return to the main conversation to steer the coordinator. The coordinator's latest result exposes the explicit review action, while specialist threads cannot independently approve, retry or cancel managed work. Shared work provides a compact list of conversations and agent assignments. Conversation links open the main workspace, and each conversation retains an Add task action. Agent results and lifecycle controls are available on demand; specialist rows link to their read-only threads. Provider configuration stays in Settings; the work list only calls out unavailable execution when action is needed.

Project agent lists separate active runs from done runs. They show live elapsed runtime, reported token usage and an approximate cost when the model's pricing is known. Runtime displays seconds for the first five minutes, then whole minutes. Usage is recorded from provider-reported input, output, reasoning and cached-token counts; cost estimates use the configured model pricing snapshot and are omitted when a rate is unavailable.

Each specialist's row and run details show its own usage and estimated cost. The supervisor displays the combined total for its own calls and its child runs, without counting specialist calls twice. Older usage recorded against the supervisor stays there; it cannot be reliably reassigned to individual specialists.

## Call telemetry and outcome review

The run retains its requested model policy. Each new tracked provider invocation also creates a `knowledge_agent_run_attempts` row: direct calls, tool follow-ups, supervisor planning, specialist work, integration review and independent review, including retries and failures without usage. Attempts record phase, supervisor generation where applicable, operation ID and the one-based retry index (`attemptNumber`). Supervisor retries share an operation ID; each invocation has its own attempt ID.

Attempt `settings` capture the application's effective request after defaults and model-specific filtering: model ID, requested versus effective reasoning effort, output/step limits, SDK retry limit, timeout, streaming and storage settings. They also record prompt, instruction and structured-output-schema hashes where applicable, application revision and adapter version. `response` keeps the provider-reported model separately from the request model, with response ID and finish reason when available. These records do not claim to know unspecified provider defaults. Hashes identify context changes but cannot reconstruct inputs or enable exact replay. Telemetry contains no prompt text, credentials or hidden reasoning; reasoning-token counts are usage metadata, not reasoning content.

Usage rows link to their invocation through `attemptId`. Missing usage is unknown, never zero; historical rows are not backfilled with attempts or invented settings. Attempt status `completed` means inference completed, not that the domain result is valid or approved. A killed process can leave an attempt `running` with usage `pending`; no terminal result is fabricated. Project-run attempts do not cover conversation title generation or the support agent.

Both provider adapters mark received usage as reported only after its persistence callback succeeds. If that callback fails, the existing error-recovery path can retry saving the retained counts; successful writes remain deduplicated by the tracked invocation. Recovery preserves the original failure outcome rather than claiming the run succeeded. It cannot recover tokens that the provider never reported, guarantee persistence during a continuing database outage, or backfill historical gaps.

To review a completed coordinator or direct run, open its existing review modal. Optionally score correctness, completeness and usefulness independently from 1–5, and select rework: none, minor, major or unusable. Any field can remain blank. Both approval and rejection retain the note and supplied scores. When an evaluation is supplied, the saved review records `rubricVersion: 1`, the original run summary and rationale, and generated artifact revision IDs—not later human edits. Supervisor output uses the exact final generation's `review.result` revision; direct output uses original version-1 revisions. Saved reviews expose these snapshots for inspection. Scores are human judgments, not engineering validation or artifact approval, and do not automatically tune models.

For authorized inspection, the existing `GET /api/knowledge/runs/:id` returns `attempts`, `usage.calls` and `approvals` under existing tenant and `knowledge:read` access checks. A parent response includes its child attempts and usage calls; review submission retains `knowledge:approve` access. Keep inference reliability, reported usage and human outcome judgments separate: do not treat missing or legacy data as zero, or approval as objective accuracy.

The project's Analytics tab reads `GET /api/knowledge/workspaces/:projectId/analytics?page=0` under existing knowledge and project read access. It pages 20 root runs at a time in stable newest-first order and recursively includes their descendants within the same tenant and project, independently of the workspace's latest-50-run window. Each usage row contributes once to the root aggregate and once to its owning agent's separate breakdown; these are alternative views, not additive totals. Attempts are matched to usage through `attemptId`. Missing input/output usage on an attempt, a member without usage records, or an unpriced usage row prevents a full cost estimate. Known priced rows remain visible as a partial recorded estimate; no priced rows means unavailable, not zero. Legacy rows without attempts remain attached to their original owner, without invented reassignment. This view excludes title generation, source processing and hosting. Refresh is explicit, with TanStack Query's 30-second stale cache and focus revalidation; it is not a live billing feed.

The same response includes a project-wide `summary`, independently of pagination. Postgres aggregates root trees and usage by `(provider, modelId)` without transferring every historical call to the browser. Recorded token totals sum known input and output tokens, never reasoning/cache subsets again. Average tokens per run uses only trees with no queued or running member, complete input/output usage for every member and no unmatched or incomplete attempt; failed or cancelled runs with complete telemetry can qualify. The response reports the qualifying denominator, incomplete records, unreported members and unpriced usage. Cost completeness does not determine token-average eligibility. Empty projects return zero run counts and null token/cost/average values, not fabricated zero usage.

## Supervisor presets

Workspace administrators can configure a provider's `Low`, `Medium`, `High` and `Ultra` presets in Settings → Agent model settings. Each preset names the supervisor model and bounded reasoning effort, then sets independent model and effort values for the required source and requirements reviewers and any enabled domain specialists. To enable a domain role, configure its model and bounded settings for the provider and effort you will use; profile instructions alone do not enable execution. Limits for parallel specialists, total assignments and supervisor revisions are stored with the preset, with the four-task ceiling unchanged. The selected preset is resolved when a run starts and its policy is snapshotted with the durable run record, so later configuration changes do not rewrite history.

Models are edited in one inline role table. Optional specialists stay in place with disabled, empty fields until enabled; enabling copies the corresponding reviewer's current settings into that row for further editing. Disabling removes that specialist from the saved preset. Independent review stays beside the effort selector, and shared execution limits are grouped below the table. Save applies the selected preset; reset restores its vendor defaults. On narrow screens, the table scrolls horizontally without widening the page. **Manage connection** opens AI connections for credentials and active-provider selection; it does not change the provider from the model editor.

In **Settings → Agent model settings**, select the effort preset and edit **Response limits**:

| Setting | Default | Allowed range |
| --- | --- | --- |
| Summary characters | 10,000 | 1,000–100,000 |
| Rationale characters | 2,000 | 500–20,000 |
| Document characters | 60,000 | 1,000–200,000 |
| Call timeout (seconds) | 180 | 10–600 |

These whole-number limits apply to the supervisor and all specialists in that preset, including independent review and direct execution. Character limits are ceilings, not requested response lengths; token budgets still apply separately. The timeout bounds each model call, not the entire run, and applies to every automatic retry. A timeout is reported explicitly with guidance to increase this setting or request a shorter answer, rather than being labeled as a generic connection failure. Higher limits can increase runtime and cost; provider-specific limits still apply.

Save the preset and **start a new request** to use changed limits. Saving never starts inference. Existing runs and ordinary retries keep their original snapshot; timeouts are not automatically retried. Legacy presets receive the defaults above for new runs. Historical supervisor snapshots retain their original character caps and phase-specific deadlines; historical direct runs retain their original 50,000-character draft cap and 60-second timeout. Reset restores the provider's vendor defaults. Changes use the existing audited, administrator-only preset workflow and do not require a database migration.

For OpenAI and Anthropic, the model fields in Settings use the connected provider credential to load the account's available model catalog. Credentials remain server-side; Settings shows a masked placeholder for a saved key and never returns its secret value. GPT 6 models and Claude Opus 5.5 / Sonnet 5.5 models are grouped first; other models returned by the provider remain selectable. Existing model IDs are retained in the selector if they are no longer returned by the catalog. Vercel AI Gateway model IDs remain manually configured because its public catalog does not indicate which models an account can use.

The workspace provider setting selects the active provider for direct and supervisor execution. Empty model IDs leave Anthropic and Vercel presets unconfigured; OpenAI retains its `gpt-4.1-mini` direct default when no model environment value is supplied. The UI does not invent or silently switch providers. Vercel presets use `provider/model` Gateway IDs at `https://ai-gateway.vercel.sh/v1` and do not fall back to OpenAI or Anthropic on a gateway failure. Vendor defaults can be restored by an administrator through Settings.

## Agent profiles

Settings → Agents separately configures workspace profiles for Supervisor (`supervisor`), Source reviewer (`source_reviewer`), Requirements reviewer (`requirements_reviewer`), Independent reviewer (`independent_reviewer`), Sound insulation specialist (`sound_insulation`), Construction law specialist (`construction_law`) and Cost options specialist (`cost_optimizer`). Users with both `knowledge:read` and `access:manage` can save plain-language role instructions, routing phrases and assigned knowledge. These controls customize the supported team; they do not enable an omitted model configuration, create new roles or grant permissions. Agent model settings control whether the independent-review pass runs for a preset; legacy and vendor presets default to off.

Use instructions for working preferences within a role, such as checking dimensions before summarizing a source. These are optional additions to the built-in runtime instructions: an empty field retains built-in behavior and does not mean the agent is unconfigured. Routing phrases are optional hints the supervisor considers while planning assignments, not guaranteed triggers. Assign only approved company-wide knowledge: project-specific or unapproved drafts cannot be selected. Company references guide the work but do not replace the project's source evidence or supply project-version citations.

Each new durable supervisor run saves the profile versions, instructions, routing phrases and assigned reference content in its own snapshot. Planning, specialist work and review use that snapshot, so later settings or knowledge edits do not rewrite the run's context. Existing runs without a profile snapshot retain the original defaults.

Workspace instructions remain subordinate to the platform safety and output contract. They cannot expand source access, change supported roles, bypass human review, approve an output, authorize external actions or relax structured output and citation validation. Engineering calculations remain unavailable until a validated deterministic tool exists.

### Planned template uploads in agent settings

Template upload and management are **not implemented yet**. The intended home is **Settings → Agents**, alongside the role's existing guidance, not a new app or separate access permission. The next workflow should let authorized administrators upload a reference PDF, inspect its extracted structure, review the reusable template and assign an immutable version to a role. Reference documents must be labeled as output examples rather than project evidence or executable instructions.

Originals and immutable file revisions should use private Railway Buckets with tenant-scoped metadata, review status and assignments in Postgres. The Knowledge app owns the template workflow and receives storage/access capabilities through its host contract. A new run should snapshot the reviewed template version along with its existing profile guidance; later uploads must not rewrite running work or historical artifact revisions. The current structured template ID/version and revision payload provide the output-side contract, but there is no upload API, template library or settings selector in this first pass. Uploading a project source today does not register it as a workspace output template.

## Runtime setup

The supervisor worker is disabled by default in local development and enabled in production with `AGENT_SUPERVISOR_ENABLED=true`. Before enabling it in a new environment, apply the standard application migrations and configure model presets. The application migration provisions the Mastra workflow checkpoint schema in `rf_agent_runtime` and copies compatible snapshots from the former runtime schema when present. The planner routes file-based work to source and requirements reviewers. Project files are readable as unreviewed evidence; human review applies to the proposed result. If a user explicitly asks to review every project source, assignments cover the available inventory or report the coverage limit.

For a new environment, apply the standard application migrations first, configure model presets, and only then enable the worker:

```sh
bun run --filter '@richtfest/api' db:migrate
AGENT_SUPERVISOR_ENABLED=true bun run --filter '@richtfest/api' dev
```

The application starts the worker with automatic Mastra store initialization disabled, so `db:migrate` must complete before queued runs can be claimed. The `db:migrate-agent-runtime` script remains available for explicit full-store setup, but it is not required for the supervisor workflow checkpoint tables. When enabled, the worker logs its startup, polling failures and per-run execution failures with the run ID and generation; repeated errors are rate-limited to keep the API log useful.

The enablement flag only turns on the worker. A workspace administrator must configure a valid model ID and bounded preset values for the selected provider and effort in Settings before starting a run. Vendor model environment variables may provide defaults, but Richtfest does not automatically choose a frontier model, infer a paid model or treat a provider API key as a complete preset. Anthropic presets omit reasoning effort because that adapter does not accept the field.

The runtime policy snapshot answers which supervisor and specialist models, limits, independent-review setting and preset version governed a run. Domain records answer what the specialists found, which source revisions support it, what the independent reviewer flagged and whether a person approved it. These are separate records: a valid runtime snapshot does not make a calculation tool available, approve a result or certify engineering or regulatory compliance.

The runtime verification uses synthetic Mastra/provider fixtures and Postgres restart and fencing tests. The domain-specialist and template extension prepares contracts and checks mock-provider execution; it does not validate engineering results or real-provider quality. Migration `0028_domain_agent_profiles` expands the profile-key constraint to all seven supported roles without rewriting existing guidance or snapshots. Apply it before saving domain profiles; source-import migrations remain separate.

## Text equivalent of the diagram

1. Project chat sends a prompt and project context to OS authentication and access checks.
2. The Mastra supervisor receives the authorized context and routes durable assignments to the generic reviewers and any domain specialists configured in the selected provider/effort preset.
3. Those specialists perform bounded review/proposal work within the existing four-task ceiling and return structured results with evidence.
4. The supervisor integrates and reviews the result set. If the preset enables independent review, a fresh reviewer pass re-reads assigned sources and can request bounded revisions. A human may steer, approve or cancel. Calculation work is unavailable in V1 and remains a future capability.
5. Mastra Postgres stores workflow checkpoints and run IDs; Richtfest Postgres stores conversations, tasks, evidence, events, approvals and policy snapshots. Private Railway Buckets store source files and revisions.
