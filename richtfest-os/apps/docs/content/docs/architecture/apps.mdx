## Ownership

Richtfest OS owns identity, sessions, roles and access, audit, provider connections, the agent runtime, the app shell and documentation. Business capabilities live in separate packages.

| Package | Responsibility |
| --- | --- |
| `richtfest-apps/crm` | Customers and contacts |
| `richtfest-apps/projects` | Projects, source files and revisions, and the shared building model |
| `richtfest-apps/knowledge` | Conversations, tasks and reviewed knowledge |
| `richtfest-apps/acoustics` | Versioned acoustic arithmetic, supplied to agents through the OS host |
| `richtfest-apps/support` | Private help conversations and reviewed bug/feature submissions |
| `richtfest-apps/public-data` | Curated public datasets, scheduled imports and immutable source releases |
| `richtfest-apps/components` | Tenant-private supplier-reference catalog, immutable content revisions and human catalog review |
| `richtfest-apps/feasibility` | Feasibility studies: keep, densify or build new compared by residual land value, with revision snapshots and a PDF report |
| `richtfest-shared` | Shared domain types, validation and permission definitions |

A business app imports its own code, shared code and external dependencies. Platform services and cross-app lookups arrive through its `src/deps.ts` host contract. App code does not import another app or OS internals.

App schemas live with their packages and are listed in the API's Drizzle configuration. User IDs in app records are plain UUIDs, not foreign keys into identity tables. Validate references against accessible workspace records before creating relationships.

The API adapts host contracts and mounts routers. One React application supplies all screens, registered through the route manifest. Boundary tests enforce this separation.

## Persistence and evidence

Postgres stores operational state, access, records, metadata, tasks and audit history. Original file contents require durable storage as well; storing only metadata does not preserve a source document.

The [Components catalog](/docs/workflows/components) retains supplier URLs and source metadata, with optional private, immutable original-PDF snapshots uploaded explicitly against a current revision's recorded checksum and page count. Sources without those values remain external-only; no automatic fetch or extraction occurs. OS storage adapters keep bytes in private Railway buckets in production and local storage in development. Migration `0034_component_documents` adds document metadata; uploading matching bytes does not change content revisions or review. Reviewed catalog revisions can inform bounded agent recommendations through OS host adapters, but are neither project source citations nor evidence of installed project components. Migration `0033_components` adds catalog tables and permissions without importing records; new keys are granted only to roles already holding `access:manage`.

TanStack Query owns server-state caching. Zustand holds local UI state. Browser caches are disposable views, never the authoritative copy of company knowledge or workflow state.

The Projects app owns the durable building, storey, room and element graph. Construction state, properties, measurements, plan-page links, placement, alternatives, review status and source reconciliation remain versioned records in Postgres. Richtfest OS supplies database, permission, audit, file and agent-runtime capabilities through the Projects host contract; the app does not import OS internals. PDF optional-content groups are a rendering control only and never become the model object hierarchy.

Agents receive a bounded snapshot of stable object IDs and reviewed facts through the Projects host. Chat may create an evidence-linked proposal against the revision it read. It cannot approve, merge or silently replace the human-reviewed model; Team and Report receive read-only context. A changed revision makes an older proposal stale instead of overwriting newer work.

### Building-plan extraction

Completing an ordinary project-evidence PDF upload creates or reuses a draft Building model and source container immediately. Once durable source processing is terminal, the Projects worker registers every packet page and queues topology only for confidently identified floor-plan sheets. Exact saved drawing-title text takes precedence over optional upload-time TypeSafe image triage; mixed, low-confidence, absent or conflicting results remain unresolved. Non-floor and unresolved pages stay in the page register with no guessed geometry. This orchestration reuses existing Postgres records and needs no migration beyond `0041_building_extraction`.

Each identified floor sheet receives a source-linked draft storey and durable extraction job. The source identity and extractor version make repeated planning and recovery idempotent; leases and a maximum of three extraction attempts bound automatic recovery. Native PDF text is preferred. If it yields no labels, the worker uses bounded German/English OCR. Topology-v5 uses supported proposed-construction fills as its primary barrier hypothesis, keeps existing/demolition fills as alternative evidence instead of unioning phases, and preserves compound even-odd fill holes. For partitioning only, it may close a doorway-sized portal between collinear, source-supported wall fragments inside one apartment domain. Exact source polygons stay unchanged, and the inferred closure is recorded as unreviewed evidence rather than a wall or door. The deterministic topology pass does not call a live model provider or populate a vector index. If TypeSafe is configured, one optional fail-open decision call classifies at most 64 deduplicated exact room-label snippets; its output is an unreviewed proposal, not extracted evidence.

Every candidate is **unreviewed** and linked to the source revision and page. Room labels seed a bounded raster topology pass. Apartment fill ownership domains constrain labels before single-label contours or wall-constrained geodesic partitions are created. Printed-area capacity checks divide shared space and demote implausible merge/split results to unresolved anchors. Conservative source-relative shape checks record bounding-box fill, compactness, rectilinearity and concavity; ordinary L-shaped rooms remain eligible, while severe tendrils or concavities become unresolved anchors. These checks are quality control only and do not establish physical scale or approve the printed area. Source fill containment supports WE-unit association; a deterministic exact-area-closure fallback may associate one otherwise unmarked apartment when its summary and rooms close to the same printed total.

An exact, nearly rectangular, clearly elongated fill on the source construction layer can become an unreviewed `draft_wall` candidate. Repeated page-relative minor-dimension bands raise its evidence tier without asserting a measured thickness. Other source polygons remain `construction_fragment` groups. Every exact polygon is retained once; wall candidates never absorb touching perpendicular shapes merely because they connect. Geodesic room-partition seams are not walls or openings.

Reference page 2 produces 87 room candidates: 73 spatial proposals and 14 unresolved anchors, with every spatial proposal assigned to one of WE1–WE11. Reference page 3 produces 91 room candidates: 74 spatial proposals and 17 unresolved anchors. On page 3, 164 of 235 exact construction polygons are draft walls, the others remain in 64 unsupported-fragment groups, and 90 printed areas remain unreviewed observations. These counts describe that reference document only. Doors, openings, adjacency, materials, room use, physical thickness, scale and complete room/wall coverage are not established. Proposed construction candidates carry only an unreviewed source-layer phase inference and do not appear in the Existing or Demolition workspace views. If extraction fails or is unavailable, the original PDF remains available for manual region entry.

Reviewers can rename a candidate, accept it as a new room or element, reconcile it to an existing same-type object, or reject it. Accepted walls become canonical `draft_wall` elements; unsupported groups become `source_construction_fragment`. Geometry retains its exact source polygons, evidence and inference limits. Printed-area observations are stripped from accepted geometry, so accepting a candidate cannot silently approve a numerical measurement. Review and reconciliation create the ordinary versioned model/review/audit records. Accepted objects enter the bounded building snapshot supplied to authorized agent runs. Agents still need the configured provider and permissions to propose changes; this context has no embedding/vector retrieval path.

Before review, authorized agents receive the same unreviewed rooms, draft walls and construction fragments in a bounded, explicitly separate `draftCandidates` collection with source revision, page and geometry quality. They are not canonical entities, calculation inputs or approvals.

Extractor upgrades and explicit re-runs reuse the page-scoped extraction job instead of creating a second candidate set. Accepted and rejected candidates remain intact; stable unreviewed candidates receive refreshed geometry and evidence, obsolete unreviewed hypotheses are superseded, and new candidates retain distinct source keys. The optional TypeSafe step is not retried independently and never prevents the deterministic job from completing.

The separate source-document model preserves extracted text blocks, the raw-text SHA-256 and PDF optional-content-group metadata for provenance and display. Those blocks are not a second semantic inventory, and their physical PDF geometry or OCG association is unknown. OCG visibility changes the evidence renderer only; it does not create, hide or redefine construction objects.
